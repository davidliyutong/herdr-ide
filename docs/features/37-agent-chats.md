# 37 · Agent chats

## Context

Coding agents run in the machines' terminals ([21](21-terminal-core.md)), where the page knows which agent runs ([25](25-agent-detection.md)) and which session it is in ([35](35-agent-native-view.md)). Reading a program's screen and files cannot stream its text, answer its permission prompts outside the terminal or confirm a message before the turn ends.

The agents have protocols of their own for running headless: Claude Code the Agent SDK's (stream-json and control requests on stdio), Codex its app-server (JSON-RPC on stdio), Antigravity (`agy`), Kimi Code and Grok the Agent Client Protocol (ACP). Through them a client starts, resumes, forks and rewinds sessions, streams text, answers permissions, questions and plans, sets model, effort and mode, compacts, tracks and stops background tasks and subagents, sends images and attached files, and reads context usage and session cost. A chat is such a session, run by a process of the product's own on the machine and drawn by the page.

Constraints: an agent runs where its files are, as the user, with the user's sign-in; nothing listens on TCP on machines; whatever is started has an owner and an end, whatever is written a bound ([10](10-remote-resource-lifecycle.md)); a session survives the page, the hub, ssh and the agent going away; the Claude protocol is unspecified and Codex's app-server experimental, so both are pinned to recorded versions.

## Goals / non-goals

Goals: chats with Claude Code, Codex, Antigravity, Kimi Code and Grok in panes on any machine; streaming text and thoughts; permissions, questions (including Codex async user questions) and plans in cards; per-provider model discovery and visibility filtering; model, effort and mode per chat, full access only where the machine allows it; click-to-compact with optional instructions; images, recursive `@` files and a standalone file picker; Markdown editing helpers and preview in the composer; Slack-style per-message queuing with withdrawal and explicit steer/interrupt; fork, rewind and switch-agent context handoff; context usage and session cost; live background tasks and subagents with stop controls; the same notifications and attention list as agents in terminals ([07](07-agent-native-workflow.md)); sessions moved between terminals and chats; chats that outlive page, hub and terminal core within bounds set per machine.

Non-goals: agents that need a terminal; OpenCode (`opencode acp` listens on an unauthenticated TCP port); editing the agents' configuration; keeping a pending permission across a host restart (the turn ends); subagents' conversations as chats.

## Design

```
page (chat pane) ──WebSocket──▶ hub (plugin chat) ───yamux──▶ agent (plugin chat, action open)
  one per page                   relay, read-only, audit,        │ a stream per connection
                                 watch → /ws and notifications   ▼
                                                             <run>/chat.sock
                                                             chat host (`chat-host`, a hidden terminal
                                                             of the instance's terminal core)
                                                             ├─ journal: chat-<host>.db
                                                             └─ adapters: claude │ codex │ acp
                                                                  └─ one agent process per live chat
```

### Agent kinds with chats

A kind of `backend/shared/agents/kinds.ts` has a chat when its row has a `chat` spec: the adapter, the command, added environment and, for ACP, the `_meta` of `session/new`. Only the adapter's name reaches the page; the command is looked up on the machine in the login shell's PATH.

| Kind     | Adapter  | Command                                                                  |
| -------- | -------- | ------------------------------------------------------------------------ |
| `claude` | `claude` | `claude` and the SDK's arguments                                         |
| `codex`  | `codex`  | `codex app-server --listen stdio://`                                     |
| `agy`    | `acp`    | `agy acp --stdio`                                                        |
| `kimi`   | `acp`    | `kimi acp`                                                               |
| `grok`   | `acp`    | `grok agent --no-leader stdio`, sessions made with `{"yoloMode": false}` |

### The chat host (`backend/features/chat/machine/host`)

`chat-host --base <data dir> --run <run dir>` (the namespace's runtime directory on the host, [40](40-shared-homes.md); the `chat-host` command of the executable, `backend/hosts/machine/chathost.ts`; Linux and macOS only) is the long-lived process that runs the agents and keeps their conversations. It serves `chat.sock` (0600) in the run directory (0700) under a lock; a second host exits. It runs as a **hidden terminal** of the instance's terminal core, so ssh, the agent and the hub may come and go while it runs. It ends after 60 s with no agent and no connection, when asked to make way for a newer build (refused while a chat is busy), or with the terminal core's stop (agents' process groups get SIGTERM, then SIGKILL); a host not gone 30 s after it began to stop kills its agents and exits. Chats stay in the journal and resume their sessions at the next prompt.

The terminal core does not read shell startup files, where agents' programs are usually put on the PATH. So the host takes the environment of an interactive login shell (`$SHELL -l -i -c env`, 10 s, 1 MiB), cached 6 hours or until a startup file changes. Agents get it without the host terminal's, ssh's and other agent sessions' variables, with `PWD` the chat's directory; `HC_SESSION`, `HC_SOCKET` and `HC_SCOPE` stay so the terminal core's crash sweep finds them. The host logs to `chat-host-<host>.log` (0600, rotated at 1 MiB once).

The host shares the same socket, lock, wire protocol, journal tables and log across releases, so a newer build takes over from an earlier host with its chats. A worker thread opens and migrates the journal, runs its statements and prunes other hosts' unused journals. A chat's events reach its clients once they are stored, in the order made ([42](42-typescript-backend.md#the-chat-host)).

### Starting the host, and handover (`backend/features/chat/machine.ts`)

The machine side has one action, `open`: a stream the hub opens, joined to the host's socket. When no host serves, the agent has the terminal core run one (`runHidden`, `backend/machine/hidden.ts`) with a minimal environment, named `veldr-chat-host` and labeled `veldr.hidden=chat-host`. If a user's own terminal holds that name, it is left alone and a fallback name (`-1`..`-16`, `agentproto.isChatHostName`) is used. The open waits up to 15 s; a name held by a host that serves nothing for that long plus 30 s is killed (only when it carries the label and matching arguments) and replaced.

A host of an older build (by `git describe`) is asked to make way when idle, and the chats resume in its successor. A newer host, one of the same commit (dirty builds carry a timestamp but compare by commit) or of unknown age is used while it speaks this protocol, so two hubs of different builds do not keep replacing each other; one that speaks another protocol fails the open with `upgrading` (503) until idle. The hub's watch opens with `start: false` and never starts or replaces a host. Other errors: `no_terminal_core` (503), `start_failed`.

### Hidden terminals

A product helper's terminal is hidden when it has both the reserved name and the label (`agentproto.hidden`); labels are free-form, so a label alone hides nothing, and clients may take neither. Every walker of the terminal core's terminals uses that rule: the terminal protocol leaves it out of snapshots, events and lists, refuses to set the label or take the name, and answers calls naming it as for a missing terminal (audited `denied.term`, `reason: hidden`, [22](22-terminal-protocol.md)); agent detection does not watch it ([25](25-agent-detection.md)); terminal history does not capture it ([36](36-terminal-history.md)).

### Chats

A chat (`c` + 16 hex digits) is one agent session in one directory. Its state is `starting`, `idle`, `working`, `waiting`, `sleeping` (no agent process), `failed` (with the end of the agent's stderr, in memory only) or `closed`; its status, for dots and notifications, is the terminal vocabulary `working`, `blocked`, `done`, `idle`.

- **Agent process.** Runs while used: idle for `chat.idleStopMinutes` (30) it ends and the chat sleeps; past `chat.maxLive` (8) the longest idle one ends. A prompt to a sleeping chat resumes the session (Claude `--resume`, Codex `thread/resume`, ACP `session/resume` or `session/load`); a session that never had a turn starts anew. Close ends the agent; archive also marks the chat seen and archived (removed first by the bounds); a prompt or unarchive brings it back; delete forgets it at once (the agent's session files stay).
- **Prompts and per-message queue.** ACP content blocks (text, images ≤ 5 MiB, `resource_link` for `@` files and attached workspace files), ≤ 8 MiB. While a turn runs, prompts default to FIFO per-message queuing (`delivery: 'queue'`) so each message stays individually withdrawable (`cancel_queued`), editable or promotable (`steer_queued`), drained one per turn completion; an explicit steer/interrupt control sends `delivery: 'steer'` (mid-turn steer where supported) or `delivery: 'interrupt'` (cancels only the active turn while preserving unrelated queued messages). A prompt carries the page's `clientId` and a stable UUID matching `EventType.User.item`; a resend of one of the last 256 is not sent twice. The first prompt names the chat until the agent's own title arrives, unless the user renamed it.
- **Permissions and questions.** The adapter asks the host, which stores a `permission` or `question` event; the first answer of any client wins (later ones get `not_found`). Secret answers are masked everywhere but to the agent. For Claude Code and Codex the host offers `allow_once`, `allow_session` (no setting written) and `reject_once`; ACP agents' own options are offered except those that allow or reject for good. Codex async (non-blocking) user questions (`isBlocking === false`) and `agentMessage` questions carry `async` and optional `autoResolutionMs`, remain answerable without blocking the turn, and are resolved as `superseded` when the user sends a new prompt or a newer async question arrives. An answer to an `agentMessage` question steers into a running turn when possible, waits in the queue when the turn cannot accept it, or starts a new turn when the agent is idle.
- **Plans.** In plan mode the plan is a permission of kind `plan` with options `plan:<mode>` (approve and continue in `default` or `acceptEdits`) and `reject_once`.
- **Modes and full access.** `default`, `acceptEdits`, `plan`, `full`; a new chat starts in `chat.permissionMode.<kind>` when set, else `chat.permissionMode` (`HostSettings.defaultModes` / `defaultMode`). Full access needs `chat.allowFullAccess` (per machine, off by default). Adapters mark which mode values grant it (for ACP every mode not known to ask, including Antigravity's `auto` and Kimi Code's `yolo`/`auto`); the host refuses them (`not_allowed`), starts such chats in `default`, sets back an agent that switches itself, and starts with full access off until the hub sends the machine's settings. A mode the agent changes to itself becomes the chat's mode.
- **Trusted folders.** An agent loads a project's own settings (hooks, MCP servers) only in a folder it trusts itself (Claude Code's `~/.claude.json`, read only) or the user trusted through the host; elsewhere it starts without them and the chat shows `untrusted_folder` with **Trust This Folder**. The host refuses `/`, the home and its ancestors, and folders others may change (`unsafe_folder`), pins the device and inode, and keeps at most 1000.
- **Model discovery, visibility, effort, compacting, usage.** Model and effort are set through the protocol, never by a slash command that saves them, and reapplied on restart; changing a configuration option on a sleeping or starting chat wakes or awaits its agent instead of failing with `sleeping`. `models` probes each adapter's live or short-lived model list (`supportedModels`, `model/list`, ACP `configOptions`/`models`) and caches the result in the host's settings table; `chat.visibleModels.<kind>` (empty = show all) filters which models appear in the composer picker while always keeping the chat's active model selectable. `compact` wakes sleeping chats if needed and maps to Claude's `/compact [instructions]`, Codex's `thread/compact/start`, and ACP `/compact [instructions]` when advertised. Context fill and session cost come from each protocol's usage messages (subscription rate-limit bars are shown by the AI usage plugin in the status bar rather than duplicated in the chat pane).
- **Fork, rewind, switch agent and export.** `fork` copies the journal up to an optional `upToSeq` and calls native session fork (`sdk.forkSession` with optional `upToMessageId`, Codex `thread/fork` read-only with optional turn boundary, ACP `session/fork` for full-session forks when advertised) or falls back to a lossy context-seeded new chat (explicitly warned before forking and marked in `Notice.Forked`); `rewind` runs only when the agent supports native rollback (`capabilities.rewind`: Claude `rewindFiles` + `resumeSessionAt`, Codex `thread/revert`), truncates the journal atomically, invalidates stale context usage (`used: 0, stale: true`), emits `EventType.Reset`, and either sends edited `content` or leaves the rewound prompt in the composer—agents without native rewind return `unsupported` and surface an explicit unsupported notice in the UI so the live session and prompt cache stay intact; `switch` transfers a conversation to a fresh native session of `targetKind` (see **Cross-agent session handoff** below); `export` returns a bounded Markdown conversation export (`host/export.ts`) or lossless raw JSON directly.
- **Cross-agent session handoff (`host/handoff.ts`).** Switching agents (`Op.Switch`, refused with `busy` while a turn runs, catching up handed-off terminal turns first) starts a fresh native session of `targetKind` and transfers context under four principles:
  1. **Budgeted selection, not AI summarization.** Context is selected deterministically from the persisted SQLite journal under a heuristic token budget derived from `chat.handoffMaxKB` (default 96 KiB / ~24k tokens, clamped 2 KiB–512 KiB) and bounded by the target model's context window when known. Chained switches (`A → B → C`) walk `Notice.Switched` lineage backwards (up to depth 8, bounded by each hop's `fromSeq`) so earlier turns keep their true per-turn agent attribution.
  2. **Retention priority without truncating the latest prompt.** Short conversations that fit the budget are preserved completely intact with no per-turn artificial truncation. Long conversations allocate budget to: the user's latest prompt first (never truncated—for prompt-injected backends the new prompt's estimated tokens are deducted from the history budget at send time), the original user request, the most recent complete turns, key command results (both failed commands and recent completed `execute` outputs, head+tail trimmed), modified file paths, and the latest plan.
  3. **Differentiated injection by backend capability.** Backends supporting direct history writes (Codex via `thread/inject_items` with `ResponseItem` user/assistant messages) inject the selected messages into the fresh thread on start (`Session.injectHistory`) and mark the chat non-fresh so sleep/resume reloads the persisted rollout; if an older Codex binary rejects the method (`-32601` → `unsupported`), the host falls back transparently to prompt-time injection. Backends without native history writes (Claude Code, ACP, fallback Codex/Fork) receive an attributed `<handoff_context>` block on the wire (`PromptParams.handoffContext`, never written to `EventType.User` or `EventType.Queued`, and not consumed by bare `/compact`) naming each prior agent and instructing the receiver to treat prior claims as historical context.
  4. **Private-state stripping and recall markers.** Private reasoning (`agent_thought_chunk`), permission state, subagent internals (`ev.parent`), live increments, and binary image payloads are stripped (`resource_link` entries keep workspace-relative paths as `[file: path]` to avoid triggering downstream `@` mention expansion). Omitted spans carry structured reference markers (turn range, source chat ID, agent kind, journal sequence range, and omitted-turn index), and the UI's `Notice.Switched` surfaces kept/omitted turn counts, estimated tokens, injection mode, and a one-click **Open previous chat** link.
- **Background tasks and subagents.** Subagent events carry `parent`, the tool call that started them, and their permissions are the chat's. Adapters publish live tasks in memory as `Chat.tasks` (`BackgroundTask[]`, cleared on agent stop, never stored in SQLite). The tray uses this list for tracked tasks and offers individual stops through `stop_task` (Claude `stopTask`, Codex `thread/backgroundTerminals/terminate` or child `turn/interrupt`). Codex settles subagents from child turn results, collaboration tool states, or subagent activity. It rechecks its live terminal list while it contains entries, including after a turn ends. Claude Code uses the SDK's background task snapshots and applies task events to the current run. ACP settles unfinished tool calls when a turn is cancelled or fails, and Antigravity clears its tracked subagent calls when the session closes.

### The protocol (`backend/shared/proto/chatproto`, version 2)

JSON lines (≤ 16 MiB) on the socket: the host's hello, then one request per connection, except `attach` and `watch`, which stay open. Agents are named by kind, never by command.

| Request                                          | Answer                                                                               |
| ------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `agents {kinds}`                                 | Availability and version per kind.                                                   |
| `models {kind, cwd?, refresh?}`                  | Cached or freshly probed `ModelOption[]` and `fetchedAt`.                            |
| `chats`                                          | Every chat, latest first.                                                            |
| `new {kind, cwd, resume?, import?, options?}`    | The chat, `starting`.                                                                |
| `fork {chat, upToSeq?, title?}`                  | The forked chat.                                                                     |
| `switch {chat, targetKind, options?, upToSeq?}`  | A new chat of `targetKind` seeded once with a handoff digest.                        |
| `export {chat, upToSeq?}`                        | Bounded Markdown conversation digest.                                                |
| `attach {chat, from, noCatchUp?}`                | The chat, its first kept sequence number, stored events after `from`, then new ones. |
| `close`, `archive`, `unarchive`, `delete {chat}` | –                                                                                    |
| `sessions {kind, cwd, cursor}`                   | A page of the agent's sessions for the directory.                                    |
| `watch`                                          | Every chat's state, then each change.                                                |
| `seen {chat, seq}`                               | –                                                                                    |
| `configure {settings}`                           | – (the machine's settings)                                                           |
| `shutdown`                                       | – (`busy` while a chat is busy)                                                      |
| `trust`, `untrust {cwd}`, `trusted`              | – / the trusted folders                                                              |
| `host_status`                                    | Version, pid, connections, live agents, sizes, settings.                             |

An attached connection sends commands answered by `ack`: `prompt` (with optional `delivery`), `cancel`, `permission`, `answer`, `set_config`, `cancel_queued`, `steer_queued`, `compact` (with optional `instructions`), `stop_task`, `rewind`, `rename`, `handoff`.

**Stored and live events.** A stored event has a sequence number and stays in the journal. A live event is an increment of an item being streamed (text, thought, tool output): unnumbered, sent only to attached connections, never stored. When the item completes, one stored event with its whole state replaces the increments, so a client that reattaches from its last sequence number drops partial items and gets them whole. Agents' stderr rides only on live events. Errors are codes the page translates.

### The journal

`chat-<host>.db` in the data directory, the host's own SQLite database ([38](38-sqlite-state.md)): chats, their stored events, trusted folders and settings.

Startup loads chats and their first kept sequence numbers together. A chat loads its saved prompt identifiers on its first identified prompt after recovery. Bounds enforcement reclaims free pages in limited batches. Live increments waiting behind journal writes have a per-chat byte and event limit. Stored events still provide the complete item.

| Bound                      | Setting              | Default | Range   |
| -------------------------- | -------------------- | ------- | ------- |
| Bytes of a chat's events   | `chat.maxChatMB`     | 64 MB   | 8–256   |
| Bytes of all events        | `chat.maxTotalMB`    | 512 MB  | 64–2048 |
| Chats kept                 | `chat.maxChats`      | 500     | 50–2000 |
| Days a closed chat is kept | `chat.retentionDays` | 30      | 1–365   |
| One stored event           | –                    | 1 MiB   | –       |

A chat over its bytes loses its oldest events; past the other bounds closed chats go, archived ones first, oldest first; a new chat with nothing left to remove is refused (`too_many`). Oversized events are cut. An event the journal refuses fails the chat, so a log never has a gap. A newer host's journal is not used; other hosts' journals on a shared home unopened for 30 days are removed.

### Adapters (`backend/features/chat/machine/{claude,codex,acp}`)

The host owns chats, logs, clients, bounds and process decisions; an adapter owns one agent process and turns its protocol into events. The rules: argv and environment as given; unserved requests answered "method not found"; unknown members passed over; the user's configuration never written; the agent in its own process group, ended gracefully before SIGKILL; output never blocked; increments live, complete items stored; a prompt recorded once; full-access values marked; a session another process runs neither resumed nor imported (`in_terminal`).

Claude Code keeps at most 16 pending prompt records. A queued prompt releases its stored content when the SDK confirms it was taken, and a settled turn retires its prompt records even if the SDK omits completion events. Codex catch-up keeps page cursors and the newest page while locating the anchor, then reads newer pages one at a time in chronological order.

- **Claude Code** (`claude/`, on `@anthropic-ai/claude-agent-sdk`): the protocol spoken by Anthropic's Agent SDK ([42](42-typescript-backend.md#claude-code)), the program run through the host's processes, the user's own `claude`; recorded with Claude Code 2.1.330. Full access needs `--allow-dangerously-skip-permissions`, so switching to it restarts the program on the same session. `CLAUDE_CODE_ENTRYPOINT` marks its sessions as the SDK's. `can_use_tool`, `AskUserQuestion` and `ExitPlanMode` become permission, question and plan; tool results are mapped by `backend/shared/agents/transcript`. A permission the program cancelled (an interrupt) is answered with a denial, as the SDK answers every request it hands on; a mode set is the one asked for, the SDK passing on no answer of the program's; lines that are no JSON objects and `keep_alive` the SDK drops itself. A session with a live `<claude dir>/sessions/<pid>.json` record is `in_terminal`. Sessions and imports read `~/.claude/projects`. The SDK is Anthropic's, all rights reserved, so no executable carries it: a machine gets the pinned npm tarball when a Claude Code chat needs it, downloading it itself or from the hub, checked against the pinned integrity, into `<data>/claude-agent-sdk/<version>`, which the chat host loads; a machine that cannot refuses the chat with `sdk_unavailable` ([42](42-typescript-backend.md#claude-code)).
- **Codex** (`codex/`): `codex app-server`, protocol v2, one per live chat. It is written against TypeScript types generated from the JSON schema Codex prints of the version pinned (`appserver.gen.ts`, by `backend/scripts/codex-schema.ts` from `spec/codex-app-server`, which `make check` holds them to): the typecheck holds the adapter to the protocol, and its tests validate the recordings and what it sends against the schema itself (`appserver.test.ts`). A thread started writable records its directory in `~/.codex/config.toml`, so threads start read-only and each turn carries the mode as policy:

  | Mode          | Approval policy | Sandbox                           | Collaboration mode |
  | ------------- | --------------- | --------------------------------- | ------------------ |
  | `default`     | `untrusted`     | `workspaceWrite` of the directory | default            |
  | `acceptEdits` | `on-request`    | `workspaceWrite` of the directory | default            |
  | `plan`        | `on-request`    | `readOnly`                        | `plan`             |
  | `full`        | `never`         | `dangerFullAccess`                | default            |

  (`default` is `untrusted` because under `on-request` the model refuses to write instead of asking.) Approvals never map to the amendments Codex saves. A command still running 2 s after an interrupt has the app-server restarted. Close closes stdin before SIGTERM: Codex killed outright leaves its shell snapshots. Its framing is its own (no `jsonrpc` member, as Codex writes it; a line over 16 MiB passed over), every message handed on in the order of the app-server's output. What it keeps of the tool calls that started and did not complete and of the subagents' threads is bounded (4096 each, the oldest going: such a call is then not marked cancelled at its turn's end, and such a thread is its own parent).

- **ACP** (`acp/`, on `@agentclientprotocol/sdk`): Antigravity (`agy`), Kimi Code and Grok. No file system or terminal capability is offered: every request of the agent but a permission is answered "method not found". One turn per prompt; prompts during a turn wait FIFO in the adapter (at most 16), with `delivery: 'interrupt'` cancelling the active turn without dropping unrelated queued messages; permissions offer the agent's `allow_once` and `reject_once` options only, at most 64 waiting. Mode mapping prefers explicit full-access values (such as Kimi Code's `yolo`) over `auto`, while mapping `full` to `auto` for agents whose autonomous mode is named `auto` (Antigravity's "Run autonomously"), always gated by `allowFullAccess`. Agents that advertise neither a mode `configOption` nor legacy `modes` (such as Grok) get a client-enforced permission mode (`default`, `acceptEdits`, `full` gated by `allowFullAccess`) initialized from the chat's mode before emitting config, backfilled on loaded sleeping/starting Grok chats so the mode selector is always available, and applied in `session/request_permission` via `allow_once` (also auto-resolving matching waiting permissions when the user switches to `acceptEdits` or `full`) without touching the agent's configuration files. `session/resume` falls back once to `session/load` when `-32603` indicates unreadable state; `session/close` runs with a bounded timeout (≤ 2 s) before process stop; `session/fork` and `/compact` are enabled dynamically when advertised by the agent (`compact()` immediately resets context usage to `0` with `stale: true`, emits `Notice.Compacting`, ignores pre-compact summarization token spikes during the compact turn, emits `Notice.Compacted` on completion, and preserves the known context window `size` when subsequent `usage_update` frames omit it); `models()` probes via `initialize` + `session/new` + `session/close`. For Antigravity (`agy`), `invoke_subagent` calls are normalized to subagent `think` tool calls and active subagents are tracked read-only via `<agy dir>/brain/<id>/.system_generated/logs/transcript.jsonl` (refusing symlinks and bounding reads/events), streaming child thoughts, tool calls and messages under `Event.parent` and publishing live subagents in `Chat.tasks`. Sessions and imports run a short agent process (`session/list` filtered to `cwd`, `session/load`, whose replay is lossy). An ACP agent cannot tell that a terminal runs a session.

Each adapter's tests replay `spec/vectors/chat/<adapter>` through a fake agent (Claude Code's through the SDK) and compare what the host gets with the golden files of the same recordings (`testdata/golden` beside the adapter's tests, edited by hand after a deliberate change of the mapping).

The seam is `backend/features/chat/machine/adapter.ts`, whose comment states the same rules for one thread:

- `Adapter`: `start(p, sink, signal)` resolves with a `Session` once the session exists (`signal` bounds the start only), `sessions(p, signal)` a page of the agent's sessions, `history(p, emit, signal)` an import's or a catch-up's stored events, and, where the adapter can tell, `inTerminal(p, signal)` the `in_terminal` error of a session another process runs. Every call gets the kind, the resolved command, the whole environment, the directory, the logger and `procs`, the host's `AgentProcesses`, through which every program is started (a process group of its own, ended gracefully; the host signals the groups when it stops).
- `Session`: `id`, `pid` (its group's), `prompt`, `cancel`, `cancelQueued`, `setConfig`, `compact`, `close` (graceful), and `done`, which settles once the agent is gone and the sink had every event, with why it ended.
- `Sink`: `event` (stored or live, returns at once), `update` (what the chat states), and `permission` and `question`, promises the user's answer settles (or the turn's cancel, or the chat's end). An adapter may call the sink from within its own methods; the host calls a session's methods only where its own state is settled.

The host gets its adapters by name from its composition root (`backend/hosts/machine/features.ts` `chatAdapters`): an adapter is added there, the host unchanged. A kind whose adapter the host was not given is refused as a kind without a chat (`unsupported`, "this host has no adapter <name>"). The host is given all three: the ACP adapter, Codex's and Claude Code's (its Agent SDK fetched on use, [42](42-typescript-backend.md#claude-code)).

### The hub's plugin (`backend/features/chat`)

**Routes** below `/api/m/{id}/p/chat/` and `/api/p/chat/` ([reference](../reference.md#http-and-websocket-endpoints)). A GET never starts a host; a read-only hub starts nothing, refuses `GET agents` and lists no sessions (both may run the agents' programs). Every change is audited as `chat.<route>`. Before a request that may start an agent the hub sends the host the machine's settings. A machine has at most 128 hub connections to its host. Expensive `POST /sessions` and `/agents` probes pass through a bounded hub-side TTL + in-flight coalescing cache (`cache.ts`, bypassed with `?refresh=1`, invalidated on host stop or machine removal, and overlaid with live watched chat states); on the chat host, probes run up to 4 concurrently with a FIFO wait queue of 16 (`probe_busy` / HTTP 429 only when full) and abort cleanly if the client disconnects. `GET /export` supports both bounded Markdown handoff digests (`format=markdown`, optional `maxBytes` bounded 2 KiB–512 KiB, structured with original request preservation, modified files, recent issues, transcript, and latest plan) and lossless raw JSON (`format=json`, redacting stderr in read-only mode); `POST /switch` and `POST /fork` accept the same `maxBytes` budget.

**The page's WebSocket** (`wire.ts`, `page.ts`; mirrored by `web/src/plugins/chat/protocol.ts`): one per page for every chat (browsers allow six HTTP/1.1 connections per origin). Each subscription is its own connection to the host; commands go on a subscription and get one `ack` each (`lost` when the subscription ended first). Flow control bounds what waits for a page; a subscription that falls too far behind is dropped by the host and reattached, without stalling the page's other chats. A read-only hub refuses commands and omits agents' stderr. Commands that change what an agent may do are audited (never a prompt's text or an answer's).

**Watch and notifications** (`watch.ts`): while a machine's host is in use, the hub watches it without starting one, sends the states to pages as the plugin's `/ws` message `states` (with the host's build and `outdated`), and publishes an agent event when a chat becomes blocked or done. When a machine disconnects its cached states become sleeping/idle with `stale: true`; a state read before the machine left never revives them (`a change after the machine left is dropped`).

### The page (`web/src/plugins/chat`, `web/src/conversation`)

- **The pane**: a layout leaf `{view: {plugin: chat, kind: chat, chat, agent}}` with the agent's brand icon in the tab and header, drawn by the conversation view from a `ChatSource`. Recent chat panes stay mounted hidden (`keptPanes.ts`) across tab, workspace and machine switches, protecting active working/waiting/starting agents from eviction so returning never remounts or triggers scroll-chasing; stopped or evicted chats persist their reading position (`atEnd`, item anchor, `scrollTop` and expanded item limit) in memory and restore it before paint on reopen. Its heading, inline-editable title, directory, state label and quick actions (Rewind turn picker, Fork, Switch Agent / Handoff dropdown with digest budget, Export dropdown with Markdown / Raw JSON and digest budget) merge into the pane's single header bar (`ChatHeader.tsx`) alongside the pane's split/zoom/close buttons. ### Importing a session, and continuing in a terminal

- **Import.** The Chats panel lists the sessions each agent kept for the directory; opening one makes a chat that resumes the session with its earlier conversation imported first (`new` with `resume` and `import`) and the agent's title. A session that already is a chat opens that chat. A terminal whose agent quit offers **Continue in Chat** in its header ([33](33-workspace-restore.md)). Two processes never write one session: the page refuses one a terminal's agent runs, the host one another process runs (`in_terminal`).
- **Handoff.** **Continue in Terminal** (Claude Code, Codex; no turn running) ends the chat's agent, marks the chat handed off, and opens a terminal tab in its directory that resumes the session by the kind's command, as a restore does ([33](33-workspace-restore.md)). A terminal already running the session is shown instead.
- **Catch-up.** When a handed-off chat is used again, the host first imports what the session did in the terminal since the last imported item. Claude Code catch-up finds that item's last occurrence and resumes at its line with the transcript state from that point.

### After the terminal core starts again

A terminal core stop ends the host and its agents. The next use starts a host that reads the journal: chats whose agent ran sleep, their turn ended in an error and pending requests cancelled. Panes reattach; the next prompt resumes the session with its context.

## Alternatives considered

| Option                                           | Why not                                                                                                                                  |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| The conversation drawn over the agent's terminal | Input pasted into a program, confirmation a turn late, permissions only in the terminal, no streaming.                                   |
| ACP for every agent                              | Claude Code and Codex speak it only through third-party adapters, without their permissions, plans, questions, effort, usage and limits. |
| The Agent SDK in Node as a sidecar               | A Node runtime per machine (often offline); the machine side runs on Bun, which loads the SDK itself.                                    |
| `character-ai/claude-agent-sdk-go`               | One-shot `claude --print` without control requests: no permissions, questions, plans, model changes, interrupts or queues.               |
| The host as a child of the agent                 | It would die with every ssh drop and hub restart; as a terminal of the terminal core it lives as the user's programs do.                 |
| A socket or port the hub reaches directly        | Nothing listens on TCP on machines; the agent's stream suffices.                                                                         |
| JSONL files per chat                             | Bounds and eviction would need their own crash-safe rewriting; SQLite gives transactions ([38](38-sqlite-state.md)).                     |
| Storing live increments                          | Every token in the log; a reattach gets the whole item instead.                                                                          |
| OpenCode through ACP                             | It listens on a TCP port without authentication.                                                                                         |

## Failure modes

- **No terminal core** → `no_terminal_core` (503).
- **Host not up in 15 s** → `start_failed`; a stuck host holding the name is killed and replaced.
- **A host of another build** → used while it speaks this protocol, else `upgrading` (503) until idle; the page offers a restart.
- **Agent not installed or not signed in** → `not_found` in the agents list; `auth_required` (the page suggests running it once in a terminal).
- **The agent exits or breaks protocol** → the chat fails with its stderr tail; the next prompt starts it again.
- **A resumed session the agent no longer has** → `not_found`.
- **The page falls behind or loses the connection** → reattach from the last sequence number; a resent prompt is taken once.
- **The journal refuses a write** → the chat fails, without a gap.
- **Pending permissions when the host ends** → cancelled, the turn ends in an error.
- **Two hubs of one instance** → one host serves both; the last configure's settings apply.
- **Unused chats** → the watch lets go after 2 minutes, agents stop after `chat.idleStopMinutes`, the host exits a minute later.

## Security

Chats run agents as the user on the machine, as terminals do. New is a long-lived product process running agents without a terminal. It is reached only through the run directory (0700, socket 0600) and the agent's stream; pages reach it only through the hub's guarded routes and WebSocket, whose inputs (kinds, chat ids, clean absolute directories, session ids, option values) are checked on the hub and again by the host. What runs is the registry's command; no command line, path or variable comes from a client. Full access is off unless the machine allows it, also after a restart; project settings load only in trusted folders no one else can change. Secret answers and stderr are never stored; stderr reaches writable clients only. The hidden terminal is no client's. See the agent-chat rows in [SECURITY.md](../../SECURITY.md).
