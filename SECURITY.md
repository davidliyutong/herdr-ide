# Security

herdr-ide gives its users interactive shells, file access and code execution
on every connected machine, with the permissions of the account running it.
Treat access to it like ssh access to all those machines.

## Threat model

**Trusted:** the user running the core, the machines it connects to (and
their herdr servers), the reverse proxy and whoever it authenticates.

**Not trusted:** other local users on the core host and on the machines,
other web pages open in the same browser, the network between browser and
proxy, and output shown in terminals.

## What the code enforces

| Risk | Mitigation |
| --- | --- |
| Web content in the desktop app reaching native APIs | Electron windows, including popups, use sandboxing, context isolation and no Node integration; only the main window has a preload, whose bridge (`desktopShell`) delivers shortcut actions and, while recording, the specs of keys pressed with cmd, ctrl or alt to the page, and accepts four signals (shortcut settings changed, recording on/off, the theme setting, of which only `system`, `dark` and `light` set the native theme, `desktop/src/policy.test.ts`; whether the page takes folders opened with the app) only from the main window's top frame on the core origin, sends that frame the paths of folders the user dropped on the Dock icon (only directories, from macOS's `open-file`; `desktop/src/folders.test.ts`), which become workspaces on the local machine as folders dropped on the sidebar do, and answers in the preload where a file the user dropped on the page is on disk (`webUtils.getPathForFile`, empty for anything else; the bridge's functions are pinned by `desktop/src/preload.test.ts`), used to create workspaces from folders dropped from Finder and to paste dropped files' paths into panes of the local machine, then reads the shortcuts from the core itself and accepts only valid specs and the known actions (`desktop/src/shortcuts.test.ts`); web security and the core CSP stay enabled. Only the exact core origin can navigate a main frame or open native windows; external HTTP(S) links open in the browser and other schemes are denied. Webviews are disabled. Only the main window relaxes the autoplay policy, for notification sounds (`desktop/src/policy.test.ts`). Permissions are denied except notifications, clipboard reads, sanitized clipboard writes and the File System Access API from the core origin inside a core window (`desktop/src/policy.test.ts`). Clipboard reads let VS Code paste from other apps, as the browser UI allows its VS Code frame after the browser's prompt; core-origin content (VS Code, its extensions' webviews) can therefore read the clipboard without a prompt. File System Access lets VS Code's **Download…** save folders and large files: it reaches only files and folders the user picks in the native dialog, and Electron keeps system folders out; a browser asks before it grants the same. |
| Desktop launcher orphaning or attaching to the wrong core | The shell accepts readiness only from its own child pipe and checks its loopback URL and port. Bind failure never reuses another service. Parent-stdin EOF cancels the core; normal quit sends SIGTERM, waits for cleanup, then kills only that child after 20 s. Single-instance locking is per Electron profile. |
| Accidental exposure of the port | Listens on loopback by default; a non-loopback `--listen` is refused unless a proxy secret is configured or `--insecure-listen` is given. |
| Requests bypassing the proxy | `--proxy-secret-file`: requests not from a same-host browser must carry `X-herdr-ide-Proxy-Secret` (constant-time comparison); the header is stripped before reaching code-server. |
| DNS rebinding, cross-site WebSocket hijacking | Host and Origin must be loopback or an `--allowed-origin`. |
| Clickjacking, script injection through served files | CSP with `script-src 'self'` and `frame-ancestors 'self'` on the UI; files are served with `nosniff`, a sandboxing CSP, and HTML/JS as `text/plain`; code-server responses get `X-Frame-Options: SAMEORIGIN`. |
| Local services of a machine running with the UI's origin | code-server's port proxy (`/proxy/<port>/`, `/absproxy/<port>/`) is disabled (`--disable-proxy`) and the core refuses those paths in any case (audited as `denied.port_proxy`), also for a code-server started by an earlier build. Otherwise a page served by any process listening on the machine, including another user's on a shared machine, could script `/ws`. |
| Abuse of herdr's API from the UI | Method allowlist (workspace/tab/pane/agent/layout/worktree calls, snapshot, plugin actions); no server control, integration or plugin installation, raw event streams or client-shell calls. `--read-only` narrows it to reads; among them `pane.copy_search` and `pane.copy_motion` (find in panes), which only read pane text that `pane.read` already returns, while `pane.scroll` stays refused (`internal/machines/machines_test.go`, `internal/server/server_test.go`). |
| Abuse of herdr's endpoint (client socket) from the UI | The browser never addresses the endpoint: the core encodes input from a closed set of events (keys, text, paste, mouse; at most 256 per message) for the owning browser only, and composes the only endpoint requests itself (`tab.focus`, `pane.focus` for the shown tab). A read-only browser sends no input, focus or colors, cannot take the session from a writable one, gets no clipboard writes, cannot make a machine reconnect (its retry is refused and audited as `denied.retry`, `internal/server/server_test.go`; a writable browser's retry replaces only a degraded session at least 5 s old and is audited as `machine.retry`), and never moves herdr's focused pane (where the session's input goes); showing a tab still focuses that tab and sizes herdr's tabs, as any herdr client does (`internal/server/surface_test.go`). |
| Paste injection | herdr wraps pastes in bracketed-paste markers but does not filter them. Pasted text loses ESC and every other C0/C1 control except tab and CR, in the browser and again in the core (`endpoint.SanitizePaste`), so a paste cannot end itself early or carry escape sequences; text and pastes are limited to 1 MiB per event. |
| Downloads exposing files | `GET /api/m/{id}/download` serves what `/file` already serves, to the same guarded origin: one file as an attachment, anything else as a zip the agent streams (at most 1000 absolute paths; the agent follows the paths named when they are links but stores links below them as links, and leaves out sockets, devices and FIFOs, so a download neither escapes into linked trees nor blocks on a FIFO). Nothing is written on the machine; a cancelled download closes the agent's stream, which stops the walk. Responses carry `nosniff` and the sandboxing CSP, are allowed in `--read-only` like viewing files, and are audited as `file.download` (`internal/server/download_test.go`, `internal/agent/archive_test.go`). VS Code's **Download (folders as zip)** sends paths the bridge extension took from the explorer to the browsers; only a page with the focus downloads them. |
| Uploads replacing or escaping files | Uploads go to the machine's upload directory under a name the server makes, or, for files dropped on a pane, into an existing absolute directory the browser names, under the file's base name without control characters; the agent claims that name (or `-1`, `-2`…) with an exclusive create, so an upload replaces no file and follows no symlink there (`internal/server/server_test.go`, `internal/agent/agent_test.go`). Uploads are at most 4 GiB, refused in `--read-only` and audited; a browser allowed to upload can already write anywhere through a pane's shell. |
| Pane programs writing the browser's clipboard (OSC 52) | Pane output is not trusted, and Chromium and the desktop app (which grants clipboard writes to the core origin) would let the page write the clipboard without a prompt. The core forwards a program's write (at most 1 MiB, never to a read-only browser). With the browser setting **Programs copying to the clipboard** at **Automatic** (the default), the browser writes it at once only within 10 s of a key, text, paste or button press it sent to a pane, the way programs answer a selection or a yank, and a toast shows the length and start of what was copied; any other write, and any write with **Ask**, is shown in a toast whose **Copy** button writes the clipboard; **Off** ignores them. A write that passed the automatic gate is also kept, for its machine only, until the next key, text, paste or left/middle press in a pane, the loss of the session or 2 minutes: meanwhile the pane menu's **Copy** and ⌘/Ctrl+C without a page selection copy it and show the same toast; writes shown with **Ask** are never kept (`web/src/__tests__/clipToast.test.ts`, `input.test.ts`). Residual: herdr does not say which pane wrote, so during those 10 s any program on the shown machine, in any pane or tab, replaces the clipboard without a click, also after input the user did not type (text VS Code sends to an agent); the toast shows only the first 60 characters. Terminals that allow OSC 52 writes (kitty, WezTerm, Ghostty) allow them at any time. **Ask** keeps every write behind the button. |
| Links in pane output (OSC 8) | Only `http:`, `https:` and `mailto:` targets are underlined or opened, with ⌘/Ctrl+click; the tooltip shows the real target. |
| Malformed or oversized data from herdr's endpoint | Frames are capped (2 MiB for the handshake, 32 MiB after); sequence lengths are checked against the bytes left before allocating, and cells (one million), hyperlinks (65,536), panes and splits (4096 each) and the cells of one patch are capped before allocating, so memory stays a small multiple of the frame; grids are limited to herdr's own bounds; trailing bytes, unknown variants and revisions that do not follow the retained surface close the connection (`internal/herdr/endpoint` tests). |
| Other users on the core host hijacking ssh | ssh control sockets live in `/tmp/herdr-ide-<uid>/s`, which must be a directory owned by the user with no group/other access, or the core refuses to start. |
| Other users on a machine | Agent state is in `~/.herdr-ide` (0700); code-server and the bridge listen only on unix sockets there (0600); nothing listens on TCP. Starting, stopping and restarting herdr's server from the UI first checks the peer credentials of whatever listens on the session's socket: another user's process gets no command and is not reported as the user's server (`foreign_server`, `internal/agent/herdr_test.go`). Residual: the pane connections to herdr's sockets (`herdr-api`, `herdr-client`) do not check the peer; herdr's default sockets are in the user's own config directory. |
| Tampered downloads | code-server releases and extensions are verified against pinned SHA-256 digests or `.sha256` sidecars; mismatches are refused. |
| Archive path traversal | Tarball extraction rejects absolute paths, `..` and links leaving the install directory. |
| Downloads made by machines (`--code-server-install=download`) | The machine fetches only `http(s)` URLs built from the core's `--code-server-url` template, with curl or wget and no shell; the tarball is checked against the digest the core knows before it is unpacked. A digest learnt on first use is recorded on the core like the core's own downloads. |
| Other users on a machine reaching the virtual display | Xvfb accepts only clients presenting its MIT-MAGIC-COOKIE-1 and runs with `-nolisten tcp`. The cookie is new at every Xvfb start and names the display; Xvfb reads its own copy (`run/xauth.server`), panes get `run/xauth` (both 0600 in the 0700 run directory), so a program changing its `XAUTHORITY` file cannot leave the server without a cookie. |
| Another user posing as the X server | X sockets live in world-writable `/tmp/.X11-unix` (libxcb before 1.16 cannot use another path), abstract ones in a namespace without permissions, and X clients cannot authenticate the server. The agent therefore uses a display number only while no lock file, socket or listener of another user is on it and `/tmp/.X11-unix` is a directory of root or the user that is sticky or not writable by group and others; it sends the cookie only to a server whose peer credentials (`SO_PEERCRED`) are this instance's Xvfb on the connection and on both its sockets (filesystem and abstract), and panes get `DISPLAY` only from a display verified this way. Residual: a pane created earlier keeps `DISPLAY=:n` after its display ended, and a program started there later reaches whatever server then takes `:n`. A display ends a minute after its last client; while herdr's server runs the display keeper is a client (the core asks for one whenever the display is ready and each time the server becomes reachable), so this needs the keeper gone with the server still running (killed, or the server restarted while the core was away); another local user who binds the abstract names of every candidate number (`:20`–`:519`) can make program windows unavailable. |
| Input to programs' windows from the browser | Window pages and their WebSockets pass the same guards as panes (Host/Origin, proxy secret, app CSP); frames are images; commands to the agent are built by the core (a viewer's refresh carries the streams all viewers decode, not its own list), and a viewer holding 64 frames or 16 MB it has not shown skips frames; closing a window (`POST /m/{id}/gui/{win}/close`, sent with `keepalive`) needs the page's own Origin like every mutation. Pages use `Referrer-Policy: same-origin`, so same-origin requests carry their Origin and other sites get no referrer. In `--read-only` mode viewers send no input, closing is refused, and a viewer can neither acknowledge frames it was not sent nor ask for the whole window more than twice a second. |
| Programs on one display | X11 does not isolate clients: every program on a machine's display (from any pane of the instance) can read and control the other windows on it, as on a desktop. |
| Fetching Xvfb on machines | Happens when a remote Linux machine connects with the GUI setting on for it, never in `--read-only` mode (which only shows a display that already runs); audited as `gui.install` and `gui.start`. `apt-get download xvfb` verifies the package against apt's signed lists (not for sources marked `[trusted=yes]`); it is unpacked with `dpkg-deb -x` into the user's `~/.herdr-ide/xvfb/` under a validated version name. Nothing runs as root. |
| Running the video encoder on machines (`gui-video`) | On by default for remote Linux machines, per machine in the settings, never pushed in `--read-only` mode. The core pushes the encoder it embeds (built from pinned, checksummed sources by `scripts/build-ffmpeg.sh`; releases build it in CI) through the agent; the agent writes it to a fresh temporary directory, compares its SHA-256 with the digest the core sent, moves it into `~/.herdr-ide/video/<digest prefix>/` (0700) and runs it only while the file there still has that digest when first used by the agent. Pushing is audited as `gui.video`. The encoder runs as the user with the agent's environment, reads raw frames from a pipe and writes packets to one; it opens no network connections, and no files beyond the GPU's: NVIDIA's driver libraries, or a render node the user may open (`/dev/dri/renderD*`) and the VA-API driver for it, which the libva built in loads from the distribution's driver directories (`/usr/lib/<triplet>/dri`, `/usr/lib64/dri`, `/usr/lib/dri`; not `/usr/local`, which a group may write) or from `LIBVA_DRIVERS_PATH`, the user's own setting. Windows larger than 4096 pixels a side are never captured whole for video. Browsers name the streams they decode in `?video=` (at most four short lowercase names); frames stay inside the guarded WebSocket like pictures. |
| Capturing windows through shared memory | The agent's window manager reads window contents through MIT-SHM into a System V segment created 0600 (only this user can attach it) and, on Linux, marked for removal as soon as the agent attached it (Xvfb attaches it afterwards), so it disappears with the agent and the display even if the agent is killed meanwhile. Other clients of the display could name the segment, which gives them nothing beyond what any program on one display can already do (see below). Without MIT-SHM, or when the segment fails, captures go through the X connection. |
| The display keeper | `herdr-ide-agent gui-keep`, started by the agent when the core asks (audited as `gui.keep`; never in `--read-only` mode) or after starting herdr's server from the UI, runs as the user and opens the instance's display like the agent: with the cookie, only to the Xvfb the instance recorded (peer credentials). It follows the herdr server that listens on the session's socket and is the user's (`SO_PEERCRED`), telling it from a later process by its start time; it sends herdr nothing (it connects and closes) and exits when the server is gone. |
| VirtualGL in every program of a pane (`--gui-gpu=all`) | Opt-in; preloads only VirtualGL's faker libraries found in system or `/opt/VirtualGL` library directories, by their resolved path, and only when the library and every directory above it belong to root and cannot be written by group or others. |
| Typing into panes to enable program windows | `POST /api/m/{id}/gui/enable` is a mutation (same guards, refused in `--read-only`, audited as `gui.enable` with the panes typed into). The core types only into known shells (bash, zsh, fish, dash, sh, ksh and similar, by executable name, so not into a program that replaced its shell with `exec`) waiting at their prompt (their process group is in the foreground, checked again right before typing): first Ctrl-C, which discards a half-typed command line, then only ` export` of the display variables it computed, each value single-quoted. A shell running a builtin such as `read` also looks idle; the text then goes to it. The audit record lists the panes typed into, busy and unreachable, also when the request fails. |
| Per-machine settings | `PUT /api/settings` with `machine` passes the same guards, accepts only machines the core knows, settings defined as per machine and, for remote-only settings, remote machines; a command-line flag still fixes the value for every machine. |
| Changing settings from the UI | `PUT /api/settings` passes the same guards as every other request, is refused in `--read-only`, accepts only defined settings with validated values (enums, absolute paths, no control characters), and is audited (`settings.set`). A setting given on the command line cannot be changed. The code-server path chosen there is run on the machines, which gives no more than the shell access the UI already has. |
| Adding, removing, renaming and reloading machines from the UI | Adding, removing and renaming run the local herdr's own commands on the core host as the user; all four pass the same guards, are refused in `--read-only` and are audited (`machine.add` with target, label and session, `machine.added`, `machine.remove`, `machine.rename` with the old and new label, `machine.refresh`; `internal/server/machines_test.go`). `GET /api/machines/add` accepts a target of printable ASCII without spaces that does not start with `-` (herdr has no `--`, so it could read as an option of herdr or ssh), a label without control characters (64 characters at most) and a plain session name; the options are passed as `--label=…` and `--remote-session=…` in one argument each, without a shell. herdr asks in the terminal before installing anything on the machine or replacing a server. `DELETE /api/m/{id}` accepts only herdr's saved machines the core knows, never the local machine or `--ssh` targets, runs `herdr machine remove ID` bounded to 30 s, and ends the machine's session like disabling it. `PUT /api/m/{id}/label` accepts the same machines and a non-empty label as above, and runs `herdr machine rename ID --label LABEL` bounded to 30 s (herdr takes the argument after `--label` as the label whatever it starts with). A reload adds only machines the core's `--machine` and `--local-only` take and keeps every machine when herdr's catalog cannot be read. The core only reads herdr's catalog. |
| Enabling and disabling machines from the UI | `PUT /api/m/{id}/enabled` passes the same guards as every other request, is refused in `--read-only`, accepts only machines the core knows and a boolean, and is audited (`machine.enable`, `machine.disable`; `internal/server/server_test.go`). The choice is saved in the core's own `machines[-<instance>].json` (0700 directory, replaced atomically), never in herdr's catalog. Disabling ends the machine's agent session, which stops what the agent started there (code-server); it gives no more than closing the connection, and panes keep running in herdr. |
| Accountability | `--audit-log` records connections, mutating calls (with the names of environment variables the core added to new panes), uploads, VS Code and bridge use, provisioning and closing program windows, and refusals. |

Not provided by herdr-ide: user authentication, TLS, rate limiting, per-user
authorization. Use the reverse proxy for these.

The desktop core has the same loopback HTTP trust boundary as CLI local use;
the launcher does not add authentication against other processes on the
host. Its app/DMG build uses ad-hoc signing, not Developer ID signing or
Apple notarization. Do not treat the build as a notarized public release.
The DMGs attached to GitHub releases are built the same way by the release
workflow; their integrity rests on `SHA256SUMS` and, for a public repository,
GitHub build-provenance attestations, both covering archives and DMGs. Only
the final publish job of that workflow holds write permissions; the build
jobs read the repository.

## Bundled herdr

Release archives include upstream herdr downloaded at build time and verified
against SHA-256 digests pinned in `internal/herdrdist` before packaging
(`internal/herdrdist/release_test.go` covers a corrupt download). At runtime
the bundled herdr is trusted like an installed one and not re-verified. The
local agent uses a copy of it in `~/.herdr-ide/herdr/` (directory 0700) only
when no installed herdr is found (`internal/agent/herdr_test.go`), with the
caller's environment and herdr's usual sockets, which herdr creates with mode
0600. herdr-ide never uploads herdr to SSH machines itself. **Update herdr**
runs the local herdr's `herdr --remote=<target>` in a terminal on the core
host (`GET /api/m/{id}/herdr/remote`: refused in `--read-only`, audited as
`herdr.remote`, SSH machines only, the target passed as one argument); herdr
then asks the user before installing anything there or stopping a server.

herdr can be managed from the UI
([17](docs/features/17-local-herdr-management.md)):
`POST /api/m/{id}/herdr/{start|stop|restart|check|update}` are mutations
behind the usual guards, refused in `--read-only` and audited
(`herdr.start`, `herdr.stop`, `herdr.restart`, `herdr.update`). The server
actions accept every configured machine, local or SSH. There they run, as
the user and with the herdr the agent found, `herdr [--session S] server`
or `herdr [--session S] server stop` (bounded to 30 s), plus the read
commands of the status (`herdr --version`,
`herdr [--session S] status server --json`) and, on Linux, the display
keeper. No argument comes from the request and nothing runs through a
shell. A listener of another user, or one that takes no connections (a
hung server), is neither stopped nor replaced. The UI asks before stopping
or restarting, which ends the terminals of that herdr session. The status
(`GET /api/m/{id}/herdr`) runs only the read commands and is allowed in
`--read-only`, for SSH machines too. `check` and `update` are accepted only
for the local machine (`internal/server/server_test.go`).
An update runs herdr's own
`herdr update --handoff` on the application's copy only: it trusts herdr's
release manifest on `herdr.dev` and the SHA-256 digests it publishes, like a
user running `herdr update`, and never changes the bundled file or an
installation of the user's. Servers are started only on request, never
automatically.

## Supported versions

Security fixes go to the latest release and to `main`.

## Reporting a vulnerability

Please report privately instead of opening a public issue: use the
repository host's private vulnerability reporting ("Report a vulnerability"
under the Security tab) or contact the maintainers. Include the version
(`herdr-ide version`), configuration flags and steps to reproduce. You will
get an acknowledgement within a few days.
