# Security

veldr gives its users interactive shells, file access and code execution
on every connected machine, with the permissions of the account running it.
Treat access to it like ssh access to all those machines.

## Threat model

**Trusted:** the user running the core, the machines it connects to, the
reverse proxy and whoever it authenticates.

**Not trusted:** other local users on the core host and on the machines,
other web pages open in the same browser, the network between browser and
proxy, and output shown in terminals.

## What the code enforces

| Risk | Mitigation |
| --- | --- |
| Web content in the desktop app reaching native APIs | Electron windows, including popups, use sandboxing, context isolation and no Node integration; only the main window has a preload, whose bridge (`desktopShell`) delivers the commands of menu items chosen (strings) to the page, accepts four signals (whether the page takes folders opened with the app; which of its menu's commands to show disabled: a list of at most 200 command ids, of which only the menu's own are used, or the list is dropped, `desktop/src/menu.test.ts`; how many panes have unsaved changes, an integer from 0 to 10000; and the page's answer when the window closes with some, one of `asking`, `close` and `stay`, `desktop/src/closeGuard.test.ts`) only from the main window's top frame on the core origin, sends that frame a request without data when the window is about to close with unsaved changes. The answer only decides whether the window closes now: `close` waives no frame's objection to unloading (the page withdraws its own, a VS Code window's still gets the native question), a page that does not take the request within 3 s, or a second close or quit while it asks, goes to the native question, which the page cannot hold, and a system shutdown never waits; a script on the core origin can still keep the window open for one close by answering slowly, sends that frame the folders the user dropped on the Dock icon or opened with the app (directories from macOS's `open-file` or from a Linux command line, a file manager's Open With, to the first launch or a second one, and the number of other items, checked in the main process and in the preload; `desktop/src/platform.test.ts`, `desktop/src/folders.test.ts`, `desktop/src/preload.test.ts`), which become workspaces on the local machine as folders dropped on the sidebar do, and answers in the preload where a file the user dropped on the page is on disk (`webUtils.getPathForFile`, empty for anything else; the bridge's functions are pinned by `desktop/src/preload.test.ts`), used to create workspaces from folders dropped from Finder and to paste dropped files' paths into panes of the local machine. The page sends the shell nothing else: the shell reads the theme, the language and the keybindings from its own core over loopback (`/ws` and `GET /api/settings`, `GET /api/keybindings`, behind the same Host/Origin guards as any client), takes only the three theme values, a language, a zoom within Chromium's limits (25–500 %) and well-formed bindings (`desktop/src/follow.test.ts`), and listens on nothing; web security and the core CSP stay enabled. Only the exact core origin can navigate a main frame or open native windows; external HTTP(S) links open in the browser and other schemes are denied. Only the main window may hold webviews, the guests of its browser panes, and the shell decides each attach (the row on web pages in the desktop app's browser pane); every other window has them disabled. Only the main window relaxes the autoplay policy, for notification sounds (`desktop/src/policy.test.ts`). Permissions are denied except notifications, clipboard reads, sanitized clipboard writes, the File System Access API and local fonts from the core origin inside a core window (`desktop/src/policy.test.ts`). Clipboard reads let VS Code paste from other apps, as the browser UI allows its VS Code frame after the browser's prompt; core-origin content (VS Code, its extensions' webviews) can therefore read the clipboard without a prompt. File System Access lets VS Code's **Download…** save folders and large files: it reaches only files and folders the user picks in the native dialog, and Electron keeps system folders out; a browser asks before it grants the same. Local fonts (`queryLocalFonts`) let the settings list the fonts installed on the computer for the terminal font: core-origin content can read the installed fonts' names and data without a prompt (a fingerprinting surface for the page, which already runs as the user's shell); a browser asks before it grants the same. The bridge also takes requests that are answered (`verifyUser`, from the same frame only): which prompt of the system the app has (Touch ID, Windows Hello or none) and whether it can keep the variable vault's unlock key (`canUnlock`: the Secure Enclave with Touch ID, or Windows Hello keys, and safeStorage); a nonce of the vault to prove, for which the shell asks the core what the nonce is for, shows that in the system's prompt, and answers with a MAC only after the user confirmed; a `session` nonce of a locked vault to unlock and a `register` nonce to enroll, for which it answers only an unlock entry's id, a MAC and a relay the page cannot read (AES-256-GCM under a key derived from the launch's verify key, bound to the nonce, the purpose and the entry), or `none` without a prompt when this install has no entry. There is one prompt at a time across the three, the shell picks its own install's entry, and anything but a well-formed nonce the core knows, with a purpose of exactly the core's shape, gets nothing (`desktop/src/verify.test.ts`, `preload.test.ts`). A script on the core origin can thus raise the prompt, whose text is the core's (for an unlock, the shell's own), not its own. On macOS the shell runs the Secure Enclave helper of its bundle (`Contents/Helpers`) by its absolute path, never through `PATH`, with one JSON line each way, at most 64 KiB, killed after 2 minutes, and takes only answers of the exact shape (`desktop/src/enclave.test.ts`); on Windows it runs PowerShell from the system directory with the Hello key's name and the challenge in the environment, never in the script (`windowsHello.test.ts`). This install's id and its secret, encrypted with safeStorage, are in `vault-unlock.json` of the app's user data, created 0600 beside it and renamed over it, and read only as a regular file of at most 4 KiB, never through a link (`desktop/src/unlockStore.test.ts`). A third answered request, `metrics`, from the same frame only, returns what the app's own processes use, for the settings' Performance page: per process Electron's kind, a helper's name, its share of a processor and its memory, at most 64 processes with text cut to 64 characters and numbers that are amounts (`preload.test.ts`); no path, command line or process id, and nothing a process holds. Native OS notifications (`notifications`, from the same frame only) validate and bound title (256 chars), body (1024 chars), tag (256 chars), boolean `silent`, enum `urgency`, and strict `pane`/`chat`/`panel` click targets on both the preload and main-process sides, cap active tracked notifications at 100, and deliver click targets only back to that frame (`desktop/src/notifications.test.ts`, `preload.test.ts`). |
| Desktop launcher orphaning or attaching to the wrong core | The shell accepts readiness only from its own child pipe and checks its loopback URL and port. Bind failure never reuses another service. Parent-stdin EOF cancels the core, and it is how the shell stops it on every system, also when Electron crashes: no signal is sent (Windows has none a process can clean up after); the shell waits for cleanup, then kills only that child after 20 s, never a terminal core (`desktop/src/core.test.ts`). The core is spawned without a shell. Single-instance locking is per Electron profile, and each instance has its own; a development instance named by `VELDR_DESKTOP_DEV` must be lowercase letters, digits and dashes and not `desktop`, and is local-only (`desktop/src/core.test.ts`). |
| Full Disk Access (desktop app on macOS) | The preload offers the page three requests that carry nothing (`desktop/src/preload.test.ts`); the shell takes them only from the main window's top frame on the core origin and only on macOS, and opens only the fixed URL `x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles`, shows in Finder only its instance's `~/.veldr-<instance>/hc/herdr-core` when that file exists, and reopens only its own bundle through Launch Services, with a helper that ends within 60 s (`desktop/src/privacy.test.ts`). Nothing grants access but the user in System Settings. `GET /api/m/{id}/privacy` (same guards as every request; allowed read-only, since it changes nothing) answers `granted`, `denied` or `unknown` for the agent's process and the terminal core, and the terminal core's path: the agent opens and closes a folder only Full Disk Access opens (`~/Library/Application Support/com.apple.TCC`, else `~/Library/Safari`) without reading it, in its own process and through the running terminal core's `machine.exec` with a fixed `/bin/sh` command and a 10 s limit (clients of `/api/v1/term` still cannot call `machine.exec`); it starts no terminal core and runs one check at a time (`internal/agent/privacy_test.go`; `backend/features/terminals/terminals.test.ts`: `routes that change state are guarded`). |
| Accidental exposure of the port | Listens on loopback by default; a non-loopback `--listen` is refused unless a proxy secret is configured or `--insecure-listen` is given. |
| Requests bypassing the proxy | `--proxy-secret-file`: requests not from a same-host browser must carry `X-veldr-Proxy-Secret` (constant-time comparison); the header is stripped before reaching code-server. |
| DNS rebinding, cross-site WebSocket hijacking, other pages of the same computer | Host must be loopback or the host of an `--allowed-origin`. Origin, when a request carries one, must be an `--allowed-origin` or, on loopback, the request's own: the same host and port as its Host header. With a port the scheme is not compared (a TLS proxy on loopback gives the page `https`); without one the scheme is what tells the ports apart, so the origin must be the `http` one. A page served from another loopback port (a development server, a port forwarded from a machine, another user's program) or under the other loopback name is another site and is refused, since the core has no login and a page's scripts could otherwise open `/ws` and the terminals' WebSocket (`backend/kernel/http/http.test.ts`: `Host and Origin`). Requests without an Origin are local programs' and plain GETs: nothing a GET does writes, and other sites cannot read the answers. The core also takes its port on the other loopback address (`::1` beside `127.0.0.1`), so that `localhost` leads to it whichever a browser tries, and vouches for the origin `http://localhost:<port>` only while it holds both (`backend/shared/host/loopback.ts`; `backend/kernel/http/http.test.ts`: `trustedOrigin`): what a browser binds to an origin, a WebAuthn credential (biometrics) for the vault, is taken only from an origin no other program can serve. When another program holds that address, or the core could not take it for any reason but the host having none, the core says so at its start and vouches for no loopback origin. Residual: a client that reaches the core through a tunnel to its loopback (`ssh -L`), or through a proxy that adds no `X-Forwarded-For` and rewrites Host to a loopback name, counts as being on the core's host. The origin `http://localhost:<port>` the core vouches for is then the client computer's, whose other loopback address the core does not hold. |
| Clickjacking, script injection through served files | CSP with `script-src 'self' 'wasm-unsafe-eval'` and `frame-ancestors 'self'` on every page of the UI, the app shell served for any of its client-side routes included (an `/api/…` path no route takes is 404, not the shell): scripts only from the core's origin, no `eval` or inline scripts; `'wasm-unsafe-eval'` lets the page compile WebAssembly, the terminal emulator served from the same origin (its digest checked by `make check`) and the small module the page builds to hand it callbacks ([26](docs/features/26-web-terminals.md); `backend/kernel/http/http.test.ts`: `appCSP` pins the policy); files are served with `nosniff`, a sandboxing CSP, and HTML/JS as `text/plain`; code-server responses get `X-Frame-Options: SAMEORIGIN`. Frames may be the UI's own (VS Code's windows) and, for the browser pane, `http` pages under the one loopback name the page is not served from, on any port: `http://127.0.0.1:*` for a page on `localhost`, `http://localhost:*` for a page on `127.0.0.1`, and none for a page on any other host (a reverse proxy's name, `[::1]`) or for the desktop app, whose panes are webviews (`backend/kernel/http/http.test.ts`: `frames`). Cookies ignore ports, so a frame that could go to the UI's own host name on another port would share that host's cookies there; the pages it can go to are other origins, which the row above refuses at the core. |
| Text the page renders as Markdown (files of machines) | The renderer (`web/src/markdown`) treats the text as untrusted. HTML in it shows as text (raw HTML is never enabled) and nothing in it becomes a script, a style or an event handler. A link keeps its target only when it is an absolute `http://` or `https://` URL or `mailto:` (a URL such as `http:/path`, which a browser resolves against the page, is none), written as the browser resolves it and never of the UI's own origin, nor, for a UI on a loopback host, of its port under another loopback name, where the core answers too (`web/src/lib/webUrl.ts`), and opens outside the page with `noopener noreferrer`; links of terminals follow the same rule (`web/src/terminal/links.ts`); a link to a file beside the document shows that file in the same preview pane; every other scheme (`javascript:`, `data:`, protocol-relative) is the link's text. An image loads only from a base64 `data:` URL of a raster type, a `blob:` URL or a file beside the document through the file route (whose path is a query parameter, so a reference cannot name another route); a remote image, which would tell its server who reads the text, becomes a link, and a path from the root (`/api/…`), with which a text could make the page send requests to the core, loads nothing. Formulas are KaTeX's markup made with `trust` off and the terminal's limits. The schemes are read as browsers read them, without the control characters and spaces they drop (`web/src/__tests__/markdown.test.tsx`). |
| Content on the UI's origin (VS Code) | code-server is proxied below `/m/{id}/code/` on the UI's own origin, so any script in a VS Code window (an extension, a webview, a page an extension opens; extensions and the files VS Code opens come from the machines, where the user's programs and anyone who can write there can change them) can do what the page can: drive the terminals of every machine, read and change their files, use a vault session of that page. VS Code is therefore off by default, with a switch per kind of client: `plugins.vscode.enabled` for the desktop app's windows and `plugins.vscode.browser` for browsers. In a browser the UI turns VS Code on only after a dialog that says what VS Code's scripts can reach and why, that it applies to every browser of this core until turned off and that the desktop app's switch is separate, and whose **Enable** works only once the user ticked that they understand the risk; the acceptance is the setting, kept in the settings file until turned off; every place that turns it on asks (the Plugins page, a VS Code pane's button, the setting's row; `web/src/__tests__/vscodeRisk.test.ts`). The core applies the requesting client's switch to every route of VS Code (code-server's status and start, the proxy with its WebSockets, the bridge's commands: `404 plugin_disabled` before code-server is prepared) and sends VS Code's bridge messages only to pages whose switch is on, so a browser never loads code-server while its switch is off, whatever the desktop app's (`backend/features/vscode/core.test.ts`: `routes follow their client's switch`; `backend/features/vscode/bridge.test.ts`: `messages follow each client's switch; the pages' theme`); turning a switch off closes that client's proxied connections and ends its requests and bridge commands in flight, and turning both off ends code-server's preparations (`backend/features/vscode/core.test.ts`: `a switch turned off ends its work`, `a switch turned off ends its requests and bridge commands in flight`, `preparations end with the last switch`). A request is the desktop app's only when it carries the token of the app's launch: 32 random bytes the app sends the core it starts on stdin (`--parent-stdio`'s hello, never in an environment that terminals, agents or code-server would inherit) and sets, before it loads the page, as a cookie for the core's origin in its own Electron session (host-only, path `/`, HttpOnly, SameSite=Strict, no expiry; `desktop/src/core.test.ts`), which the core compares in constant time; no token configured, no cookie or a wrong one is a browser. No script reads the HttpOnly cookie, browsers never get it, and the proxy removes it before a request reaches code-server (`backend/features/vscode/proxy.test.ts`: `is not forwarded`). Nothing code-server answers outlasts the switch: the proxy drops `Service-Worker-Allowed` from its responses (code-server allows `/` for its own worker), so no service worker of VS Code's content can claim a scope above its script's path, where it would control the UI's own pages, and drops every `Set-Cookie` that names the desktop app's cookie (`backend/features/vscode/proxy.test.ts`: `response headers`); while VS Code is off for a page's kind of client, the page unregisters every service worker of the origin, all of them VS Code's content's since the UI registers none (`web/src/__tests__/vscodeWorkers.test.ts`). A request checks its client's switch again once it took the context its work follows, so a request that passed the route's check just before VS Code was turned off starts no work, nor a preparation of code-server, that nothing would end (`backend/features/vscode/work.test.ts`: `work is taken only while its client's switch is on`). The page learns its kind of client from the core (`client` in `GET /api/settings`), not from the preload's bridge. Residual: cookies are kept per host, not per port, so a request the desktop app's windows make to another port of `127.0.0.1` carries the token too; only content in those windows can make one, and the token only makes a request count as the desktop app's, which a process on the host can do without it through the loopback API. With VS Code on, its content keeps the page's access: serving code-server from an origin of its own would close that. |
| Local services of a machine running with the UI's origin | code-server's port proxy (`/proxy/<port>/`, `/absproxy/<port>/`) is disabled (`--disable-proxy`) and the core refuses those paths in any case (audited as `denied.port_proxy`), also for a code-server started by an earlier build. Otherwise a page served by any process listening on the machine, including another user's on a shared machine, could script `/ws`. |
| A machine's local services in the browser pane (port forwards) | A forward is a listener of the core on the core host's loopback only, on both loopback addresses (on `127.0.0.1` alone only where the host has no `::1`; a port whose other address another program holds, or that could not be taken for another reason, is not used: `backend/shared/host/loopback.ts`; `backend/features/browser/browser.test.ts`: `listenLoopback`), that carries each connection to a port of the machine's own loopback through the agent (`dial` connects to `127.0.0.1` or `::1` and nothing else; `internal/agent/plugin/browser/browser_test.go`). It exists from a writing request of a client on the core's own host (a loopback peer and Host, no proxy; `403` otherwise), audited with its ports, until it is stopped, unused for `browser.forwardIdle` minutes, its machine removed, the plugin turned off or the core stopped; at most 32, 128 connections each (`backend/features/browser/browser.test.ts`: `refusals`, `ends and bounds`, `reaper`, `connections bound`). A use is a connection accepted, bytes carried or a pane asking for the forward: a connection that only stays open keeps nothing and ends with its forward (`backend/features/browser/browser.test.ts`: `idle is about use`), and a listener that fails for good ends its forward instead of leaving it listed (`backend/features/browser/browser.test.ts`: `listener failures`). The page asks for a forward only after the user's own action in it: an address or a port typed into a pane, a port chosen in **Ports**, a link to a remote machine's loopback ⌘/Ctrl-clicked in one of its terminals (whose tooltip names the address), or **Forward and open** confirmed in a pane. A link clicked in a document shown in a preview pane (Markdown of a machine, not trusted, whose text can hide the address) is not: it names its address in its tooltip, and its pane uses the forward that exists or asks, naming the machine and the port with the whole address in its field (`web/src/__tests__/browserDocLinks.test.tsx`). It asks for none for a window that a page shown in a pane opens (a loopback address there is the user's own computer's, or an existing forward's when it is on that forward's local port), nor for a view found in the layout, which every client and every script of the page writes: such a pane uses the forward when it exists and asks when it does not, also once the forward it used has ended, and a view that names another machine than its layout's gets no request (`web/src/__tests__/browserPane.test.tsx`, `browserPopup.test.ts`, `browserLinks.test.ts`, `browserDocLinks.test.tsx`). By default (`browser.openLinks`) only loopback addresses of terminals and documents open in a pane; any other address opens in the system's browser, without a referrer, as the user's own click. A document's link to the core host's own loopback (the UI on a loopback host) loads in a pane without a forward: a request to that computer's service, as the same click in the browser would make, from a sandboxed frame or the browser partition, without the UI's cookies. The core's own address, under any loopback name, is no page for a pane, typed, linked or found in a view (`browserAddress.test.ts`, `terminalLinks.test.ts`). Nothing listens on the machine. The forwarded page is another origin than the UI (its own port), which the guard refuses at the core; the frame loads it under the loopback name the UI is not served from, the only one the page's `frame-src` names, so no cookie of the UI's host reaches it, also when the framed page navigates itself (`backend/kernel/http/http.test.ts`: `frames`); in a browser it is a sandboxed frame that cannot navigate the UI's window. Residuals: while a forward exists, every program and user of the core host can connect to it, as with `ssh -L`, and what answers is whatever listens on that port of the machine, another user's service on a shared machine included. A forward is plain TCP on a predictable loopback port without a Host check, so any web page open in the user's browsers can send it requests whose answers it cannot read (and a name rebound to loopback reaches services that ignore Host), again as with `ssh -L`. A client that reaches the core through a tunnel to its loopback (`ssh -L`), or through a proxy that adds no `X-Forwarded-For` and rewrites Host to a loopback name, counts as being on the core's host, so forwards made from it listen on the core's computer, not the client's. |
| Web pages in the desktop app's browser pane | The pane shows any `http(s)` page in a `<webview>`, which only the main window may hold and only its page on the core's origin may attach: the shell allows an attach only for the partition `persist:browser` and an `http(s)` address without credentials that is not the core's, and rewrites the guest's preferences whatever the page asked (no preload, no Node integration anywhere, sandboxed, context isolated, web security on, no webview of its own; `desktop/src/policy.test.ts`). The partition has its own cookies and storage: the cookie that marks the app's own requests lives in the default session only, so the core takes a guest's requests for a browser's, and refuses them by their origin. The partition grants no permission but full screen (the app has no prompt to ask with). A guest navigates to `http(s)` addresses only and never to the core's own port under any loopback name (the UI is no page for a pane, where the core would take it for one more browser), and a window it opens is not opened: its address goes to the page, which shows it as a new browser tab, three within ten seconds for one guest (scripts open windows without the user, and Electron blocks none). That tab leads into no machine: the page makes no forward for it (the row above). A guest's page whose name did not resolve offers its address to the system's browser: the line names the host, the button's tooltip the address, which is `http(s)` and not the core's own (`safeWebUrl`), and only the user's click opens it (`web/src/__tests__/browserWebview.test.tsx`); other failures offer nothing. Residual: a page shown in a pane can navigate itself to a name that does not resolve to have the button offered, so a user who clicks it opens an address the page chose in the system's browser, with the sessions there. Host names resolve with the system's resolver in every session of the app (`hostResolver`), and every session uses the system's proxy settings. |
| A read-only page making machines reconnect | A read-only page's `retry` over `/ws` is refused and audited as `denied.retry`, and the machine keeps its session (`backend/features/machines/core.test.ts`: `retry`), since a connection attempt may start an ssh login; a writable page's `retry` only ends the wait before a disconnected machine's next attempt. |
| Paste injection | The page's emulator encodes pastes with Ghostty's paste encoder: bracketed when the program asked for it, with unsafe control characters (ESC among them) replaced, so a paste cannot end itself early or carry escape sequences (`web/src/__tests__/vt.test.ts`). The core passes terminal input on unchanged: a client allowed to write a terminal can type anything into it anyway. |
| Downloads exposing files | `GET /api/m/{id}/download` serves what `/file` already serves, to the same guarded origin: one file as an attachment, anything else as a zip the agent streams (at most 1000 absolute paths; the agent follows the paths named when they are links but stores links below them as links, and leaves out sockets, devices and FIFOs, so a download neither escapes into linked trees nor blocks on a FIFO). Nothing is written on the machine; a cancelled download closes the agent's stream, which stops the walk. Responses carry `nosniff` and the sandboxing CSP, are allowed in `--read-only` like viewing files, and are audited as `file.download` (`backend/features/files/transfers.test.ts`: `files and archives`, `read-only mode downloads, as it shows files`; `internal/agent/archive_test.go`). VS Code's **Download (folders as zip)** sends paths the bridge extension took from the explorer to the browsers; only a page with the focus downloads them. The extension's `closePane` (VS Code's key for closing in a window without editors), closes only the pane whose iframe of that window has the page's keyboard, as Close Pane would (undoable, not in read-only mode, not under a dialog; `backend/features/vscode/bridge.test.ts`: `close, leave, download`; `web/src/__tests__/desktop.test.ts`); its `leave` (the key that gives the keyboard back to the page) moves that page's keyboard to the pane's header (and, as `bridge.focus` does, records which window that pane shows); it changes nothing on a machine. A download started with a page's random id (`dl=`) is reported as progress events (id, saved name, sizes, state, a reason code; never contents) only to the page that follows that id over its WebSocket (`download.watch`), so other pages, read-only ones included, learn neither the names nor the ids; it can be broken off with `download.cancel`, which needs that id, changes nothing on a machine and is audited as `file.download.cancel`; every download in progress is followed (its state goes with its request), how one ended is kept 10 minutes (at most 256) for a page that reconnects, and one cancelled before its request arrived is refused (`backend/features/files/transfers.test.ts`: `progress, ends and cancels`, `edges`). An archive is complete only with the agent's end mark: one cut short by a lost connection aborts the response instead of saving a truncated zip. |
| Uploads replacing or escaping files | Uploads go to the machine's upload directory under a name the server makes, or, for files dropped on a pane, into an existing absolute directory the browser names, under the file's base name without control characters; the agent claims that name (or `-1`, `-2`…) with an exclusive create, so an upload replaces no file and follows no symlink there (`backend/features/files/names.test.ts`: `upload into a directory`; `backend/features/files/transfers.test.ts`: `into a directory and into the upload directory`; `internal/agent/agent_test.go`). Uploads are at most 4 GiB, refused in `--read-only` and audited; a browser allowed to upload can already write anywhere through a pane's shell. |
| The file explorer changing files (plugin `files`) | Its changes (`POST /api/m/{id}/p/files/{mkdir,mkdirs,create,rename,move,copy,trash,remove,write,upload}`) are mutating routes: refused in `--read-only`, where the panel offers none, behind the same guards, and audited as `files.<action>` with the machine, the paths it acted on (the first 50 of a list, with their count) and how it ended (`backend/features/files/explorer.test.ts`: `audit targets`, `changes`). They act with the user's permissions, as the pane's shell does, with guardrails against slips: the agent refuses the root, every directory that holds the home directory (the home directory too) and its own data directory and anything in it, also when a link in the path's directory leads there, and a save does not write through a link into them (`TestRefusedPaths`). Adding an authenticator derives the key again from that request's passphrase, as an extractable copy that lives for that request only, to wrap it for the new entry. The vault is locked after every start, the key is never written anywhere in the clear, and the file opens nothing without the passphrase or an authenticator's key-encryption key (its unlock entries and the passphrase's window: *Proving the user without the passphrase*); a lost passphrase cannot be recovered. The key is not kept from swap by locked memory, and the core does not limit its core dumps for it: native memory, swap and a core dump of the core process can hold the key, as they can the passphrase and PRF output of a request (JavaScript strings, which cannot be wiped), the ephemeral private key while an unlock entry is made, the launch's verify key, and in the desktop shell the strings of what makes a desktop key-encryption key and the helper's answer; a debugger of the same user (ptrace) is outside the model. Changing the passphrase installs the new key only once every value is sealed under it and written: a change that fails (a value that does not open) leaves a locked vault locked (`backend/features/vault/store.test.ts`: `values are bound to their name, machines and flag`), and the same write drops every unlock entry (`backend/features/vault/store.test.ts`: `a lock forgets the key; a new passphrase seals everything again and ends the unlock entries`). Argon2id parameters read from the file are bounded (16-byte salt, time 1–10, memory 8 MiB–1 GiB, 1–16 threads) and a file outside them is refused at open, so an edited file cannot weaken the derivation or exhaust the core's memory (`backend/features/vault/store.test.ts`: `other versions, damaged files and derivations out of bounds do not open`). A new vault's first passphrase needs no session (it has no values yet): when the passphrase was set is shown in the panel, on hover over its unlock card and its bar, so one a program set instead of the user shows to a user who looks. The file can still be attacked offline by guessing the passphrase, which Argon2id slows down; the panel shows a strength bar, and its passphrase fields keep password managers away (a passphrase a browser saved is readable by the user's programs in several browsers). |

| Proving the user without the passphrase (the vault's authenticators) | Biometrics stand in for the passphrase in two ways. A **proof** holds no key: the authenticators are sealed with the key (not readable in the file, another vault's or an edited one does not open), so a proof opens a session of an unlocked vault or allows a request and never unlocks a locked one, and every lock (Lock, `vault.autoLock`) forgets the key and ends every session and nonce (`backend/features/vault/core.test.ts`: `a WebAuthn credential with PRF is added, proves, and unlocks`; `backend/features/vault/store.test.ts`: `a lock forgets the key; a new passphrase seals everything again and ends the unlock entries`). An **unlock** gives a locked vault its key back from the authenticator's unlock entry: the master key wrapped with AES-256-GCM in the vault's file under a key-encryption key (HKDF-SHA256) that only the authenticator gives again, from the P-256 ECDH secret of the desktop app's Secure Enclave key (usable only after Touch ID with the fingerprints enrolled when it was made, on that Mac) and an ephemeral key of the core of which only the public half is kept, or from the Windows Hello key's signature of a challenge of the core, each with a secret the shell keeps with safeStorage, or from a WebAuthn credential's PRF output for a salt of the core (vectors in `spec/vectors/vault-unlock/`; `backend/features/vault/store.test.ts`: `KEKs`; `desktop/src/relay.test.ts`). The wrap's additional data binds the entry's id, authenticator, kind, every parameter and the hash of the file's check, so an edited entry does not open and a new passphrase ends every entry, also one an older build changed (`backend/features/vault/store.test.ts`: `an edited entry does not open: refused, or dropped when malformed`, `a lock forgets the key; a new passphrase seals everything again and ends the unlock entries`, `an older build's write keeps the entries; a new passphrase ends them, also one an older build set`); the key is not wrapped again after an unlock, since it does not change until the passphrase does. The key is installed only once the KEK opened the wrap, the key opened the check, the guard it opens holds the entry's authenticator (else the entry goes: `backend/features/vault/store.test.ts`: `a passphrase-made entry wraps the key the passphrase gives`), a PRF unlock's assertion of the nonce verified with the stored key and a counter that grows (`backend/features/vault/core.test.ts`: `a WebAuthn credential with PRF is added, proves, and unlocks`), and the passphrase's window holds: less than the lesser of `vault.passphraseDays` (14 days by default, 1–90) and the days sealed with the passphrase since it was last checked with the key, sealed under the key so that a program that writes the file can only put an older window back or remove it (`backend/features/vault/store.test.ts`: `an unlock entry opens only within the passphrase's window`; `403 passphrase_due` outside it); Require Passphrase (`POST /api/p/vault/lock` with `{"forget": true}`) removes the window. An unlock's session is a proof's, and its automatic lock is at most the time sealed with the window (`backend/features/vault/core.test.ts`: `the automatic lock follows the setting: a change shortens an unlock, never lengthens it; an authenticator's unlock is capped by the time sealed with the window`). An unlock whose key does not open or verify counts as a wrong passphrase; what guesses nothing is refused without counting, and a dead desktop entry (a relay that opened, a wrap that did not) is removed as `409 unlock_stale`, uncounted (`backend/features/vault/core.test.ts`: `the desktop app's MAC proves, and its relay enrolls and unlocks`); every removal is audited as `vault.unlock_removed`, and no key, relay content or PRF output is logged or audited (`backend/features/vault/core.test.ts`: `a WebAuthn credential with PRF is added, proves, and unlocks`). The desktop app's secrets reach the core through the page in a relay: AES-256-GCM under HKDF-SHA256 of the launch's verify key, bound to the nonce, the purpose and the entry, opened only for a request of the desktop client and only for those (`backend/features/vault/store.test.ts`: `relays`; `backend/features/vault/core.test.ts`: `the desktop app's MAC proves, and its relay enrolls and unlocks`); the page carries it and can neither read nor make one. A proof answers a nonce of the core (32 random bytes, one try, two minutes, bound to its purpose: a session, one request with one answer, one variable to show or to grant; while the vault is locked only a session's, good for an unlock only and ended by the unlock; at most 32 wait; they end with the sessions). A WebAuthn credential's assertion is checked by `@simplewebauthn/server`, with the checks beyond it that the Go core made kept (`backend/features/vault/webauthn.ts`): the challenge (compared as bytes), the ceremony, the page's origin and no cross-origin use, the host name's hash, the user present **and verified**, the signature (ES256, RS256 with at least 2048 bits, EdDSA) with the stored key, a counter that grows where the authenticator counts, and PRF required; every input is bounded and malformed ones are refused, failing the check and nothing else (`backend/features/vault/webauthn.test.ts`). A browser keeps a credential for a host name, whatever the port, and a program of the core host chooses the headers of its requests, so neither the host name nor the request's `Origin` says which page asked: each credential is bound to the origin it was added from, which must be the one the authenticator signed, and credentials are added, taken and unlock only for origins the core vouches for (the row on other pages of the same computer): an `--allowed-origin`, or `http://localhost` on the core's own port while it holds that port on both loopback addresses. Adding an authenticator needs a session the passphrase opened, the passphrase again (slowed down as every check) and a proof by the new authenticator, and wraps the key for it in the same step for a lock (`backend/features/vault/core.test.ts`: `a lock asked for during an add comes after the authenticator and its unlock entry`): a WebAuthn credential without PRF is refused (`400 prf_required`), and so is a new desktop authenticator without its relay (`backend/features/vault/core.test.ts`: `a WebAuthn credential with PRF is added, proves, and unlocks`); one entry per install of the app (at most 4) and per credential (`backend/features/vault/store.test.ts`: `entries are bounded: one per install, at most 4, one per credential; their input and authenticator are checked`). Exempting an app needs a session the passphrase opened and the passphrase again (`403 passphrase_required` without it, `backend/features/vault/core.test.ts`: `an exempt app reads without asking while unlocked`); a new passphrase removes the authenticators, their entries and the exemptions, and removing an authenticator removes its entries in the same write. A session a proof or an unlock opened answers requests and changes and shows variables, but does not change what guards the vault (authenticators, exempt apps, the rule below, imports, exports: `401 vault_passphrase`), so biometrics never widen what biometrics or an app may do. With **Verify every Allow** (kept in the vault, not a setting, which programs change without the gate) no session lets a value out: allowing a request, showing a value to the page, and letting a variable be read by another machine or seen by the model where it was only injected each need a proof made for that very action or the passphrase again, and ending the rule needs the passphrase with the request; a guard that does not open counts as the rule on (`backend/features/vault/core.test.ts`: `where every Allow is verified, a session lets nothing out`). What else would let a value out later takes the passphrase with its request whatever the rule: adding an authenticator, exempting an app, an export (`backend/features/vault/core.test.ts`). With the rule, then, a program driving the user's unlocked page, with its session of the passphrase, a proof or an unlock, gets no value out, which is what the row above leaves open; what it can still do is what a session does that lets nothing out: change values and descriptions (it can put its own token under a variable's name, or words for the agents in a description), add, rename and delete variables, import a file of its own over them, narrow who may read, remove authenticators and exemptions, lock the vault and require the passphrase. Without the rule a session allows, shows and widens as before. The automatic lock's time is a setting, which programs change without the gate: a change shortens the time of a vault that is unlocked but does not lengthen it; a longer time, or never, counts from the next unlock with the passphrase (`backend/features/vault/core.test.ts`: `the automatic lock follows the setting: a change shortens an unlock, never lengthens it; an authenticator's unlock is capped by the time sealed with the window`). Residual: a browser's WebAuthn prompt names the site, not the request, so content on the UI's origin (VS Code, while on) can raise it for a request of its choosing and the user who confirms without reading the page allows it; the desktop app's prompt names the machine and the variables. A key-encryption key or PRF output obtained once, with any copy of the vault's file, gives the master key offline until the passphrase changes: the window bounds only unlocks through the core, and removing an authenticator or Require Passphrase is no revocation against a program that kept an older copy of the file and writes it back (the core reads the file at its start; nothing in the file can count against a rollback); revocation is a new passphrase. `vault.passphraseDays` and `vault.autoLock` are settings, changed without the gate: a program of the core host can raise them (to 90 days, to never) before the user next types the passphrase on a locked vault, which seals them into the window, at most for 90 days. A program of the user cannot answer Touch ID, Windows Hello or a passkey but can cause their prompts: it can run the helper (or a program of its own) with an entry's blob, which the file holds, and a reason of its own text; on macOS the shell's secret is in the keychain under the app's access list (another program gets the keychain's prompt); on Windows DPAPI gives the shell's secret to any program of the user and a Hello key can be opened by name and asked to sign, with a dialog that names no purpose, so there only the Hello prompt stands, and a PowerShell transcript, if the user turned transcription on, could record the signature. A PRF output is a long-lived secret that passes through the page's script and the request's body: content on the UI's origin that sees it once, with the vault's file, has the master key. An administrator who sets the clock back after the passphrase lengthens the window, which counts by the wall clock. Availability is not defended: a program can delete the file or a Hello key, require the passphrase without a session, or make the passphrase wait with failed unlocks. A program that can write the vault's file can put back an older sealed guard or remove it, and with it the rule, as it can replace the file. The shell's word is as good as the shell: a program that can read the memory of the user's processes has the key of the launch, and one that can rewrite the app's bundle (notably the ad-hoc build that `make desktop-install` puts in `/Applications`) can replace the helper or the shell's code. Programs of the core host can use up the waiting nonces, which delays a proof. |

Not provided by veldr: user authentication, TLS, rate limiting, per-user
authorization. Use the reverse proxy for these.

The desktop core has the same loopback HTTP trust boundary as CLI local use;
the launcher (the Electron shell) does not add authentication against
other processes on the host. The token of its launch only tells the
core which requests are the app's windows', for VS Code's switches. The macOS DMG and zip are signed ad hoc
unless the release workflow has the Developer ID secrets, in which case
they are signed with that identity and notarized; the Windows setup and
the Linux AppImages and deb packages are not signed. Chromium's sandbox
stays on everywhere: the app never passes `--no-sandbox`, and on Ubuntu
24.04 and later the deb installs the AppArmor profile it needs there. The
integrity of release files rests on `SHA256SUMS` and, for a public
repository, GitHub build-provenance attestations, both covering the
archives and every installer. Only the final publish job of that workflow
holds write permissions; the build jobs read the repository. Every action
of the workflows is pinned by its full commit id (`.github/workflows/`).

On macOS the desktop app's vault unlock secret is sealed with Electron's
safeStorage, whose key is in the login keychain item `<APP_NAME> Safe
Storage`, trusted by the build that made it alone; a build without a Team
ID (signed ad hoc or with the user's own certificate) is another identity
after every rebuild. The shell moves the item to its own build once
(`desktop/src/keychain.ts`, `keychain.test.ts`): it reads the old password
with `/usr/bin/security` (a prompt that names `security`), deletes the old
item, has safeStorage make a new one and seals every instance's secret
again. The old password stays in the main process's memory until this
instance's file is written; a failure puts the old item back, trusted by
the app alone, with the password on `security -i`'s standard input, never
in an argument. `security` and `codesign` run by absolute path, bounded in
time and output. Always Allow on that prompt would let any program read
the old item through `security` until the shell deletes it a moment
later.

Claude Code receives `--allow-dangerously-skip-permissions` only when a
full-access start or mode change passed the host's existing policy gate.
A mode change ends the old process before starting its replacement; a new
chat before its first turn reuses its own session id rather than resuming
a conversation that has not been saved (`TestRestartFullBeforeFirstTurn`).
Existing conversations are resumed, and busy turns still refuse the restart
(`TestRestartFull`); no agent configuration is written.

Builds of local changes carry their build time in their version only to
be told apart: a host of another such build is never asked to make way
(`TestDirtyBuildKept`); the page reminds the user to restart it, through
the existing `POST host/stop` (a mutating, audited route, refused on a
read-only core and while a chat works or waits). The terminal core and
the user's terminals keep running.

## Embedded herdr-core

The core embeds upstream herdr-core for the agent to install on machines
([21](docs/features/21-terminal-core.md)). The build downloads the release
archives and checks them against SHA-256 digests pinned in
`internal/hcdist`; it fails on a mismatch. The executable is taken from the
same bytes that were verified, as the one regular file named `herdr-core`
at the archive's root (64 MiB at most; a link, a directory or a second entry
of that name is refused), and is never run during a build
(`internal/hcdist/release_test.go`). The core hands the agent the SHA-256
of the uncompressed executable with every install
(`backend/kernel/payloads.ts`, `backend/hosts/bun/payloads.ts`;
`backend/kernel/payloads.test.ts`: `herdr-core: its digest is of the
uncompressed executable; a damaged or missing one has none`;
`backend/features/terminals/terminals.test.ts`:
`installs and starts the build’s terminal core`), and the agent accepts
only a file with that digest.

## Reporting a vulnerability

Please report privately instead of opening a public issue: use the
repository host's private vulnerability reporting ("Report a vulnerability"
under the Security tab) or contact the maintainers. Include the version
(`veldr version`), configuration flags and steps to reproduce. You will
get an acknowledgement within a few days.
