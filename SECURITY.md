# Security

herdr-ide gives its users interactive shells, file access and code execution
on every connected machine, with the permissions of the account running it.
Treat access to it like ssh access to all those machines.

## Threat model

**Trusted:** the user running the core, the machines it connects to, the
reverse proxy and whoever it authenticates.

**Not trusted:** other local users on the core host and on the machines,
other web pages open in the same browser, the network between browser and
proxy, and output shown in terminals.

## What the code enforces

| Risk | Mitigation |
| --- | --- |
| Web content in the desktop app reaching native APIs | Electron windows, including popups, use sandboxing, context isolation and no Node integration; only the main window has a preload, whose bridge (`desktopShell`) delivers the commands of menu items chosen (strings) to the page, accepts two signals (whether the page takes folders opened with the app, and which of its menu's commands to show disabled: a list of at most 200 command ids, of which only the menu's own are used, or the list is dropped; `desktop/src/menu.test.ts`) only from the main window's top frame on the core origin, sends that frame the folders the user dropped on the Dock icon or opened with the app (directories from macOS's `open-file` or from a Linux command line, a file manager's Open With, to the first launch or a second one, and the number of other items, checked in the main process and in the preload; `desktop/src/platform.test.ts`, `desktop/src/folders.test.ts`, `desktop/src/preload.test.ts`), which become workspaces on the local machine as folders dropped on the sidebar do, and answers in the preload where a file the user dropped on the page is on disk (`webUtils.getPathForFile`, empty for anything else; the bridge's functions are pinned by `desktop/src/preload.test.ts`), used to create workspaces from folders dropped from Finder and to paste dropped files' paths into panes of the local machine. The page sends the shell nothing else: the shell reads the theme, the language and the keybindings from its own core over loopback (`/ws` and `GET /api/settings`, `GET /api/keybindings`, behind the same Host/Origin guards as any client), takes only the three theme values, a language, a zoom within Chromium's limits (25–500 %) and well-formed bindings (`desktop/src/follow.test.ts`), and listens on nothing; web security and the core CSP stay enabled. Only the exact core origin can navigate a main frame or open native windows; external HTTP(S) links open in the browser and other schemes are denied. Webviews are disabled. Only the main window relaxes the autoplay policy, for notification sounds (`desktop/src/policy.test.ts`). Permissions are denied except notifications, clipboard reads, sanitized clipboard writes, the File System Access API and local fonts from the core origin inside a core window (`desktop/src/policy.test.ts`). Clipboard reads let VS Code paste from other apps, as the browser UI allows its VS Code frame after the browser's prompt; core-origin content (VS Code, its extensions' webviews) can therefore read the clipboard without a prompt. File System Access lets VS Code's **Download…** save folders and large files: it reaches only files and folders the user picks in the native dialog, and Electron keeps system folders out; a browser asks before it grants the same. Local fonts (`queryLocalFonts`) let the settings list the fonts installed on the computer for the terminal font: core-origin content can read the installed fonts' names and data without a prompt (a fingerprinting surface for the page, which already runs as the user's shell); a browser asks before it grants the same. |
| Desktop launcher orphaning or attaching to the wrong core | The shell accepts readiness only from its own child pipe and checks its loopback URL and port. Bind failure never reuses another service. Parent-stdin EOF cancels the core, and it is how the shell stops it on every system, also when Electron crashes: no signal is sent (Windows has none a process can clean up after); the shell waits for cleanup, then kills only that child after 20 s, never a terminal core (`desktop/src/core.test.ts`). The core is spawned without a shell. Single-instance locking is per Electron profile, and each instance has its own; a development instance named by `HERDR_IDE_DESKTOP_DEV` must be lowercase letters, digits and dashes and not `desktop`, and is local-only (`desktop/src/core.test.ts`). |
| Full Disk Access (desktop app on macOS) | The preload offers the page three requests that carry nothing (`desktop/src/preload.test.ts`); the shell takes them only from the main window's top frame on the core origin and only on macOS, and opens only the fixed URL `x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles`, shows in Finder only its instance's `~/.herdr-ide-<instance>/hc/herdr-core` when that file exists, and reopens only its own bundle through Launch Services, with a helper that ends within 60 s (`desktop/src/privacy.test.ts`). Nothing grants access but the user in System Settings. `GET /api/m/{id}/privacy` (same guards as every request; allowed read-only, since it changes nothing) answers `granted`, `denied` or `unknown` for the agent's process and the terminal core, and the terminal core's path: the agent opens and closes a folder only Full Disk Access opens (`~/Library/Application Support/com.apple.TCC`, else `~/Library/Safari`) without reading it, in its own process and through the running terminal core's `machine.exec` with a fixed `/bin/sh` command and a 10 s limit (clients of `/api/v1/term` still cannot call `machine.exec`); it starts no terminal core and runs one check at a time (`internal/agent/privacy_test.go`, `TestHCEndpointsGuard`). |
| Accidental exposure of the port | Listens on loopback by default; a non-loopback `--listen` is refused unless a proxy secret is configured or `--insecure-listen` is given. |
| Requests bypassing the proxy | `--proxy-secret-file`: requests not from a same-host browser must carry `X-herdr-ide-Proxy-Secret` (constant-time comparison); the header is stripped before reaching code-server. |
| DNS rebinding, cross-site WebSocket hijacking | Host and Origin must be loopback or an `--allowed-origin`. |
| Clickjacking, script injection through served files | CSP with `script-src 'self' 'wasm-unsafe-eval'` and `frame-ancestors 'self'` on every page of the UI, the app shell served for any of its client-side routes included (an `/api/…` path no route takes is 404, not the shell): scripts only from the core's origin, no `eval` or inline scripts; `'wasm-unsafe-eval'` lets the page compile WebAssembly, the terminal emulator served from the same origin (its digest checked by `make check`) and the small module the page builds to hand it callbacks ([26](docs/features/26-web-terminals.md); `TestCSPOnAppShell` pins the policy on the shell, a client-side route and an unknown API path); files are served with `nosniff`, a sandboxing CSP, and HTML/JS as `text/plain`; code-server responses get `X-Frame-Options: SAMEORIGIN`. |
| Content on the UI's origin (VS Code) | code-server is proxied below `/m/{id}/code/` on the UI's own origin, so any script in a VS Code window (an extension, a webview, a page an extension opens; extensions and the files VS Code opens come from the machines, where the user's programs and anyone who can write there can change them) can do what the page can: drive the terminals of every machine, read and change their files, use a vault session of that page. VS Code is therefore off by default, with a switch per kind of client: `plugins.vscode.enabled` for the desktop app's windows and `plugins.vscode.browser` for browsers. In a browser the UI turns VS Code on only after a dialog that says what VS Code's scripts can reach and why, that it applies to every browser of this core until turned off and that the desktop app's switch is separate, and whose **Enable** works only once the user ticked that they understand the risk; the acceptance is the setting, kept in the settings file until turned off; every place that turns it on asks (the Plugins page, a VS Code pane's button, the setting's row; `web/src/__tests__/vscodeRisk.test.ts`). The core applies the requesting client's switch to every route of VS Code (code-server's status and start, the proxy with its WebSockets, the bridge's commands: `404 plugin_disabled` before code-server is prepared) and sends VS Code's bridge messages only to pages whose switch is on, so a browser never loads code-server while its switch is off, whatever the desktop app's (`TestCodeRoutesFollowTheirClientsSwitch`, `TestBridgeMessagesFollowTheClientsSwitch`); turning a switch off closes that client's proxied connections (`TestVSCodeOffEndsItsWork`). A request is the desktop app's only when it carries the token of the app's launch: 32 random bytes the app sends the core it starts on stdin (`--parent-stdio`'s hello, never in an environment that terminals, agents or code-server would inherit; `TestReadHello`) and sets, before it loads the page, as a cookie for the core's origin in its own Electron session (host-only, path `/`, HttpOnly, SameSite=Strict, no expiry; `desktop/src/core.test.ts`), which the core compares in constant time; no token configured, no cookie or a wrong one is a browser. No script reads the HttpOnly cookie, browsers never get it, and the proxy removes it before a request reaches code-server (`TestDesktopCookieNotForwarded`). Nothing code-server answers outlasts the switch: the proxy drops `Service-Worker-Allowed` from its responses (code-server allows `/` for its own worker), so no service worker of VS Code's content can claim a scope above its script's path, where it would control the UI's own pages, and drops every `Set-Cookie` that names the desktop app's cookie (`TestDesktopCookieNotForwarded`); while VS Code is off for a page's kind of client, the page unregisters every service worker of the origin, all of them VS Code's content's since the UI registers none (`web/src/__tests__/vscodeWorkers.test.ts`). A request checks its client's switch again once it took the context its work follows, so a request that passed the route's check just before VS Code was turned off starts no work, nor a preparation of code-server, that nothing would end (`TestVSCodeWorkTakenOnlyWhileOn`). The page learns its kind of client from the core (`client` in `GET /api/settings`), not from the preload's bridge. Residual: cookies are kept per host, not per port, so a request the desktop app's windows make to another port of `127.0.0.1` carries the token too; only content in those windows can make one, and the token only makes a request count as the desktop app's, which a process on the host can do without it through the loopback API. With VS Code on, its content keeps the page's access: serving code-server from an origin of its own would close that. |
| Local services of a machine running with the UI's origin | code-server's port proxy (`/proxy/<port>/`, `/absproxy/<port>/`) is disabled (`--disable-proxy`) and the core refuses those paths in any case (audited as `denied.port_proxy`), also for a code-server started by an earlier build. Otherwise a page served by any process listening on the machine, including another user's on a shared machine, could script `/ws`. |
| A read-only page making machines reconnect | A read-only page's `retry` over `/ws` is refused and audited as `denied.retry`, and the machine keeps its session (`TestReadOnlyRetryKeepsTheSession`, `internal/server/server_test.go`), since a connection attempt may start an ssh login; a writable page's `retry` only ends the wait before a disconnected machine's next attempt. |
| Paste injection | The page's emulator encodes pastes with Ghostty's paste encoder: bracketed when the program asked for it, with unsafe control characters (ESC among them) replaced, so a paste cannot end itself early or carry escape sequences (`web/src/__tests__/vt.test.ts`). The core passes terminal input on unchanged: a client allowed to write a terminal can type anything into it anyway. |
| Downloads exposing files | `GET /api/m/{id}/download` serves what `/file` already serves, to the same guarded origin: one file as an attachment, anything else as a zip the agent streams (at most 1000 absolute paths; the agent follows the paths named when they are links but stores links below them as links, and leaves out sockets, devices and FIFOs, so a download neither escapes into linked trees nor blocks on a FIFO). Nothing is written on the machine; a cancelled download closes the agent's stream, which stops the walk. Responses carry `nosniff` and the sandboxing CSP, are allowed in `--read-only` like viewing files, and are audited as `file.download` (`internal/server/download_test.go`, `internal/agent/archive_test.go`). VS Code's **Download (folders as zip)** sends paths the bridge extension took from the explorer to the browsers; only a page with the focus downloads them. The extension's `closePane` (VS Code's key for closing in a window without editors), closes only the pane whose iframe of that window has the page's keyboard, as Close Pane would (undoable, not in read-only mode, not under a dialog; `TestBridgeClose`, `web/src/__tests__/desktop.test.ts`). A download started with a page's random id (`dl=`) is reported as progress events (id, saved name, sizes, state, a reason code; never contents) only to the page that follows that id over its WebSocket (`download.watch`), so other pages, read-only ones included, learn neither the names nor the ids; it can be broken off with `download.cancel`, which needs that id, changes nothing on a machine and is audited as `file.download.cancel`; every download in progress is followed (its state goes with its request), how one ended is kept 10 minutes (at most 256) for a page that reconnects, and one cancelled before its request arrived is refused (`TestDownloadProgress`, `TestDownloadEdges`). An archive is complete only with the agent's end mark: one cut short by a lost connection aborts the response instead of saving a truncated zip. |
| Uploads replacing or escaping files | Uploads go to the machine's upload directory under a name the server makes, or, for files dropped on a pane, into an existing absolute directory the browser names, under the file's base name without control characters; the agent claims that name (or `-1`, `-2`…) with an exclusive create, so an upload replaces no file and follows no symlink there (`internal/server/server_test.go`, `internal/agent/agent_test.go`). Uploads are at most 4 GiB, refused in `--read-only` and audited; a browser allowed to upload can already write anywhere through a pane's shell. |
| The file explorer changing files (plugin `files`) | Its changes (`POST /api/m/{id}/p/files/{mkdir,mkdirs,create,rename,move,copy,trash,remove,write,upload}`) are mutating routes: refused in `--read-only`, where the panel offers none, behind the same guards, and audited as `files.<action>` with the machine, the paths it acted on (the first 50 of a list, with their count) and how it ended (`internal/plugins/files/audit_test.go`). They act with the user's permissions, as the pane's shell does, with guardrails against slips: the agent refuses the root, every directory that holds the home directory (the home directory too) and its own data directory and anything in it, also when a link in the path's directory leads there, and a save does not write through a link into them (`TestRefusedPaths`). It compares file identities (`os.SameFile`), not names: the home directory resolved fully and every directory above it along both its configured and its real path, and every directory holding the path once the links of its directory are followed, against the data directory, so a home that is a link (`/home/me -> /data/me`) or a name in another case on a case-insensitive volume (`/Users/ME`) is refused too (`TestRefusedThroughLinkedHome`, `TestRefusedInAnotherCase`); where a move or copy lands is checked as well, also behind a link to the destination folder, and a folder is never copied or moved into itself through a link (`TestCopyIntoLinkInsideItself`). Renames and moves never replace a file (`RENAME_NOREPLACE`, `RENAME_EXCL`; across file systems a copy that replaces nothing, then a removal), copies take a free name, Delete moves to the user's trash (freedesktop.org layout, `~/.Trash` on macOS) and deleting for good is asked first; it opens each directory relative to its parent without following a link and removes links without following them, as `os.RemoveAll` does, and stops between entries when the core stops waiting (`TestRemoveTree`). The trash at the top of another mount, where other users may write (`/tmp`), is used only when it cannot hand the files to them: an administrator's `.Trash` must have the sticky bit and not be a link, and the user's `.Trash/<uid>` or `.Trash-<uid>` and their `files` and `info` must each be a directory of the user, not a link, without access for others (made `0700` when missing); a planted one makes the trash unavailable, and the panel asks before deleting for good (`TestMountTrash`; the top is found along the path's real directory, `TestMountTopFollowsLinks`). A save is at most 8 MiB, received in full before the file is touched, and written as VS Code writes a user's file: in place, through a descriptor opened without following a link anywhere on the file's real path (`O_NOFOLLOW_ANY` on macOS, `openat2` with `RESOLVE_NO_SYMLINKS` on Linux 5.6 and later; where those are missing only the file's own name), without blocking and without taking a controlling terminal, then checked to be a regular file (a FIFO or a device is never written), with the precondition checked again on that descriptor, so the file checked is the file written: a change made on the machine since the editor loaded it is a `409 conflict`, never overwritten unless the user chooses to, and a link swapped in for the file or a directory above it is a conflict even then (`TestSaveRefusesALinkAboveTheFile`); it is then truncated, written and synced. A save creates nothing but a new file where none is (with what the umask leaves of `0666`, never replacing one or following a link there): no temporary file and no backup, beside the file or elsewhere, so the save leaves nothing of its own for another user who may rename entries of the file's directory to swap, and a file keeps its inode, links, owner, group, mode, extended attributes and ACLs; one the user may not write stays as it is, mode included (`internal/agent/plugin/files/save_test.go`: `TestSaveInPlace`, `TestSaveInUnwritableDirectory`, `TestSaveRefusesWhatIsNotAFile`, `TestSaveChecksTheFileItOpens`). The cost is VS Code's: a write that fails after the truncation (a full disk) leaves part of the text in the file and answers `partial_write`, and the editor keeps the text to save again (`TestSaveFailureIsPartial`); a program reading the file during the write can read part of it. Remaining risk, as with VS Code (which checks less): a save the user forces (**Overwrite**, **Save Again**, an upload's **Replace**) writes whatever regular file is at the path when it is opened, so another user who may rename entries of its directory (theirs, or one they may write that is not sticky) and may hard-link the user's files (macOS; Linux with `fs.protected_hardlinks` off) can put a link to another of the user's files there and have its content replaced by the user's text; a save that is not forced finds the size and time changed and stops. Uploads from the explorer (at most 4 GiB, streamed) pass the same guard, are received in full into the agent's own `staging/` directory (`0700`, files `0600`) before anything at the target changes (one cut short leaves nothing there; what an agent killed meanwhile left is removed after 7 days, `TestPruneStaged`, and an agent whose session ended waits up to 5 s for the requests still running to remove theirs, `TestServeWaitsForRequestsToClean`), are written into a new file under a free name, created only where nothing is, unless the user chose Replace, which writes the file as a save does, and are audited with their path, size and `replace` (`internal/agent/plugin/files/upload_test.go`); lists of paths hold at most 1000, stats 200, and at most 8 stats run at once on a machine, one per path (`internal/agent/plugin/files/files_test.go`). Polling stats directories only while the panel is shown. |
| Pane programs writing the browser's clipboard (OSC 52) | Terminal output is not trusted, and Chromium and the desktop app (which grants clipboard writes to the core origin) would let the page write the clipboard without a prompt. The page's emulator takes a program's write (up to Ghostty's limit; a read-only page ignores them, `web/src/vt/clipboard.ts`). With the browser setting **Programs copying to the clipboard** at **Automatic** (the default), the browser writes it at once only within 10 s of a key, text, paste or button press it sent to a terminal, the way programs answer a selection or a yank, and a toast shows the length and start of what was copied; any other write, and any write with **Ask**, is shown in a toast whose **Copy** button writes the clipboard; **Off** ignores them. A write that passed the automatic gate is also kept, for its machine only, until the next key, text, paste or left/middle press in a terminal or 2 minutes: meanwhile the pane menu's **Copy** and ⌘/Ctrl+C without a page selection copy it and show the same toast; writes shown with **Ask** are never kept (`web/src/__tests__/clipToast.test.ts`). Reading the clipboard (OSC 52 `?`) is never answered. Residual: during those 10 s any program in a terminal the page shows replaces the clipboard without a click, also after input the user did not type (text VS Code sends to an agent); the toast shows only the first 60 characters. Terminals that allow OSC 52 writes (kitty, WezTerm, Ghostty) allow them at any time. **Ask** keeps every write behind the button. |
| Links in pane output (OSC 8) | Only `http:`, `https:` and `mailto:` targets are underlined or opened, with ⌘/Ctrl+click; the tooltip shows the real target. |
| Other users on the core host hijacking ssh | On Linux and macOS ssh control sockets live in `/tmp/herdr-ide-<uid>/s`, which must be a directory owned by the user with no group/other access, or the core refuses to start (`TestCheckPrivateDir`). |
| ssh from a core on Windows | Win32-OpenSSH has no ControlMaster, so the core keeps no control sockets: `transport.ControlDir` is empty, ssh gets no `Control*` option and no `ssh -O stop` is run (`TestSSHArgsWithoutControlDir`). Every connection runs in BatchMode with the user's keys, ssh agent and known hosts; an interactive login, whose result nothing would keep, is refused (`GET /api/m/{id}/auth` answers `501 ssh_login_unsupported` after the target check, `GET /api/config` reports `ssh_login: false`; `TestSSHLoginNeedsAControlDir`), so host keys are accepted and keys unlocked outside the app, in the user's own terminal. ssh is started without a console window (`CREATE_NO_WINDOW`) and with `--` before the target as everywhere. The local machine has no agent there and is never dialed (`local_unsupported`, `TestLocalMachineWithoutAnAgent`). |
| Other users on a machine | Agent state is in `~/.herdr-ide` (0700); code-server and the bridge listen only on unix sockets there (0600); nothing listens on TCP. The bridge's and the vault's sockets are served by the newest agent of the instance, which takes them over (replacing the file in the 0700 run directory, which only the user can), and the others serve them again once they are free: an agent removes a socket on exit only while it is its own (same inode), so an agent that lingers after a reconnect neither keeps the connections nor leaves the path unserved (`TestSocketsFollowTheNewestAgent`). |
| Tampered downloads | code-server releases and extensions are verified against pinned SHA-256 digests or `.sha256` sidecars; mismatches are refused. |
| Archive path traversal | Tarball extraction rejects absolute paths, `..` and links leaving the install directory. |
| Downloads made by machines (`--code-server-install=download`) | The machine fetches only `http(s)` URLs built from the core's `--code-server-url` template, with curl or wget and no shell; the tarball is checked against the digest the core knows before it is unpacked. A digest learnt on first use is recorded on the core like the core's own downloads. |
| Git from the browser (plugin `git`) | Every action runs the `git` executable on the machine with an argument vector the agent builds for that action: no shell, no option or flag from the request. Paths are relative to the repository's top level, without `.` or `..` elements, after `--` and literal, each with git's `:(literal)` magic (not `GIT_LITERAL_PATHSPECS`, which the agent drops from its environment like every other `GIT_*` variable it does not keep, and which hooks would inherit); many paths are split over several runs rather than one command line over the system's limit; revisions and names never start with `-`, contain none of git's special characters, and are resolved before use (`rev-parse --verify`, `show-ref --verify`, `check-ref-format` for new names, remotes from `git remote`; a branch pulled from a chosen remote goes as `refs/heads/<name>` after `check-ref-format`), so values such as `--upload-pack=…` or `--exec=…` are refused (`TestArgvRefusesOptions`, `TestLiteralPaths`). git runs without a terminal (its own session), without askpass programs, with `GIT_TERMINAL_PROMPT=0` and the agent's environment without `SSH_ASKPASS`, the locale and every `GIT_*` variable except `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_SSH_VARIANT`, `GIT_AUTHOR_*` and `GIT_COMMITTER_*` (so `GIT_DIR`, `GIT_CONFIG_*`, `GIT_ATTR_SOURCE`, `GIT_EXEC_PATH`, `GIT_TRACE*`… cannot redirect it; `TestEnviron`): a fetch, pull or push that needs credentials fails with `auth_required` and the UI suggests a terminal (`TestAuthRequired`). The remotes' URLs the panel shows come without a URL's user information (also one whose password holds a raw `/`, `?`, `#` or `@`; an `@` past the first `/` is the path's only when what precedes that `/` reads as a host and port, as git and curl read it), query and fragment (`?access_token=…`), and without an scp-like address's user with a password (everything before its last `@`), where tokens are often put (`TestRedactURL`). Reads take no optional locks and run without the repository's file system monitor (`core.fsmonitor=false`, `core.untrackedCache=false`), maintenance (`maintenance.auto=false`, `gc.auto=0`) and textconv drivers (`--no-textconv`, `--no-ext-diff`), so opening the panel on a cloned repository runs none of the programs its configuration names there (`TestReadsRunNoMonitor`). The exception is `git.autoFetch`: above 0 (off by default; never in `--read-only`, where the panel changes nothing) the panel fetches every remote on its own while it shows a repository, which runs the programs the repository's configuration names for a fetch (`core.sshCommand`, `remote.<name>.uploadpack`, credential helpers) without a click, as a fetch the user starts does; the setting's description says so. Residual: `status` and `diffStat` still run the clean filters (`filter.<name>.clean`) the repository's attributes and configuration name for changed files, as a git-aware shell prompt does, also for a `--read-only` viewer. Changes (`POST /api/m/{id}/p/git/{change}`) are mutating routes, refused in `--read-only` and audited as `git.<action>` and, when they ended, `git.<action>.done` with the repository, the revisions, refs and names, the mode, a stash's commit, the flags (`force`, `forceWithLease`, `amend`, `all`), the number of paths and the result, never a patch or a message (`TestChangeAudit`). The diff pane reads a file of the working tree only inside the repository: a link to a directory outside is not followed, and the file is opened without following a link or blocking on a FIFO, at most 8 MiB (`TestWorktreeBlobLinks`). Each run has a timeout (15 s reads, 120 s changes) after which its process group is killed, as when the request ends; a run whose git exited ends 2 s later although a program it left (a hook's `indexer &`, also one that left the group) holds its output, and that program is not killed (`TestBackgroundChild`); at most 8 runs at once per machine, another fails with `busy` after 3 s (`TestBusy`); output (32 MiB), files (8 MiB), patches and messages are bounded. Hooks and, for changes, the repository's configuration run as they would in the user's terminal. |
| Terminal clients (`/api/v1/term`) | The WebSocket passes the same Host, Origin and proxy-secret guards as every request. herdr-core's API also runs commands, reads and writes files and reaches other machines; clients get only an allowlist of methods about terminals and documents (`termReadMethods`, `termWriteMethods` in `internal/server/term.go`), never `machine.*`, `file.*`, `server.*` or a call with `on` (another machine of that core); refused calls are audited (`denied.term`, a call refused for `on` included), and `terminal.run` (its `argv`, `cwd` and the names, never the values, of the variables the client gave in `env`), `terminal.kill`, `terminal.rm`, `terminal.interrupt` and `terminal.keep` are audited with their terminal; an `env` that is not an object of strings is refused. Attaching is a message of its own, so a client cannot open herdr-core channels itself. Output is credited end to end: a client's `ack` returns at most the output the core sent it on that stream and it has not acknowledged, so it cannot make a terminal core send ahead of what it draws, and a client that stops reading is disconnected (`TestTermProtocol`, `internal/server/term_test.go`). |
| Read-only terminal clients | With `--read-only` a client of `/api/v1/term` may subscribe to machines, call the reading methods (`terminal.list`, `terminal.get`, `terminal.read`, `doc.get`, `templates.list`) and attach as an observer; writing methods are refused (`read_only`). An observer's attach carries no display facts and cannot take the terminal's size; its input, automatic input, `resize`, `focus` and `facts` are dropped; its focus does not mark an agent's finished turn as seen for other clients; its credit is cut to the output it was sent. The core installs, starts and restarts no terminal core for it (`TestTermReadOnly`). |
| Large messages on the terminal protocol | `/api/v1/term` reads messages of at most 16 MiB; a larger one ends the connection. |
| Connections to machines' terminal cores | A machine's terminal backend (the core's connection to that machine's terminal core through the agent) is opened by its first subscriber and closed 10 s after the last subscriber left; the terminal core and its programs keep running there, as they belong to the user's account, until stopped from the UI. |
| The agent's herdr-core (ops `hc`, `hc-api`) | herdr-core's API has no authentication of its own: whoever reaches its socket runs commands as the user. The agent puts the socket in its run directory (0700), sets the socket itself to 0600 after a start and a restart (herdr-core creates it 0755 and relies on the directory), and reaches it only through the `hc-api` pipe; nothing listens on TCP. The executable is written to a temporary file in `~/.herdr-ide/hc/` (0700), accepted only when its SHA-256 equals the digest sent with the install (64 MiB at most), and then renamed into place (`internal/agent/hc_test.go`). Before a start or a restart the core sends the digest of the executable this build carries, and the agent hashes the installed file again (not from its cache) and runs it only when they are equal (`bad_digest` otherwise); a development build that carries no executable sends none, and the installed one runs (`TestHCVerifiedBeforeStartAndSocketPrivate`, which checks the socket's mode after both as well). Machines are mapped by id, and an ssh machine only when the file (which seals each machine's kind and target with the variables) names it with the same kind and target as the machine of that id on this core: an id alone need not be the same machine on another core (an `--ssh` machine's id is its target, a record imported from herdr's catalog keeps herdr's id), so an export naming `devbox` does not let this core's `devbox` of another target read without asking (`TestImportMapsMachinesByTarget`); the local machine only when its label matches too, never by label alone, so an import never lets a machine read without asking that the file did not name by its id and target; the others, and every ssh machine of a file written before targets were recorded, ask every time. A target is compared as written: an ssh alias that this core's ssh configuration resolves to another host than the exporting core's did counts as the same machine, and the preview lists the machines the file maps. The core keeps nothing of a file between the preview and the import. |
| What the vault's MCP server exposes | The MCP server (`<slug>-mcp`, the `mcp` command) runs with the privileges of the CLI that starts it and talks to it only over stdio; it exits when stdin closes or on SIGTERM, SIGINT or SIGHUP, and kills the commands it still runs first. Masking does not catch values that are encoded (base64), split or transformed, and the command can send them anywhere it can reach: `inject_only` keeps a value out of `get_variable`, not out of a command written to print it encoded (`internal/vaultmcp/mcp_test.go`). Not provided by herdr-ide: user authentication, TLS, rate limiting, per-user
authorization. Use the reverse proxy for these.

The desktop core has the same loopback HTTP trust boundary as CLI local use;
the launcher (the Electron shell) does not add authentication against
other processes on the host. The token of its launch only tells the
core which requests are the app's windows', for VS Code's switches. The macOS DMG and zip are signed ad hoc
unless the release workflow has the Developer ID secrets, in which case
they are signed with that identity and notarized; the Windows setup and
the Linux AppImages and deb packages are not signed. Chromium's sandbox
stays on everywhere: the app never passes `--no-sandbox`, and on Ubuntu
24.04 and later the deb installs the AppArmor profile it needs there. The
integrity of release files rests on `SHA256SUMS` and, for a public
repository, GitHub build-provenance attestations, both covering the
archives and every installer. Only the final publish job of that workflow
holds write permissions; the build jobs read the repository. Every action
of the workflows is pinned by its full commit id (`.github/workflows/`).

## Embedded herdr-core

The core embeds upstream herdr-core for the agent to install on machines
([21](docs/features/21-terminal-core.md)). The build downloads the release
archives and checks them against SHA-256 digests pinned in
`internal/hcdist`; it fails on a mismatch. The executable is taken from the
same bytes that were verified, as the one regular file named `herdr-core`
at the archive's root (64 MiB at most; a link, a directory or a second entry
of that name is refused), and is never run during a build
(`internal/hcdist/release_test.go`). The core hands the agent the SHA-256
of the uncompressed executable with every install
(`internal/embedded/embedded_test.go`), and the agent accepts only a file
with that digest.

## Supported versions

Security fixes go to the latest release and to `main`.

## Reporting a vulnerability

Please report privately instead of opening a public issue: use the
repository host's private vulnerability reporting ("Report a vulnerability"
under the Security tab) or contact the maintainers. Include the version
(`herdr-ide version`), configuration flags and steps to reproduce. You will
get an acknowledgement within a few days.
