# Security

herdr-ide gives its users interactive shells, file access and code execution
on every connected machine, with the permissions of the account running it.
Treat access to it like ssh access to all those machines.

## Threat model

**Trusted:** the user running the core, the machines it connects to, the
reverse proxy and whoever it authenticates.

**Not trusted:** other local users on the core host and on the machines,
other web pages open in the same browser, the network between browser and
proxy, and output shown in terminals.

## What the code enforces

| Risk | Mitigation |
| --- | --- |
| Web content in the desktop app reaching native APIs | Electron windows, including popups, use sandboxing, context isolation and no Node integration; only the main window has a preload, whose bridge (`desktopShell`) delivers the commands of menu items chosen (strings) to the page, accepts one signal (whether the page takes folders opened with the app) only from the main window's top frame on the core origin, sends that frame the folders the user dropped on the Dock icon or opened with the app (directories from macOS's `open-file` and the number of other items, checked in the preload; `desktop/src/folders.test.ts`, `desktop/src/preload.test.ts`), which become workspaces on the local machine as folders dropped on the sidebar do, and answers in the preload where a file the user dropped on the page is on disk (`webUtils.getPathForFile`, empty for anything else; the bridge's functions are pinned by `desktop/src/preload.test.ts`), used to create workspaces from folders dropped from Finder and to paste dropped files' paths into panes of the local machine. The page sends the shell nothing else: the shell reads the theme, the language and the keybindings from its own core over loopback (`/ws` and `GET /api/settings`, `GET /api/keybindings`, behind the same Host/Origin guards as any client), takes only the three theme values, a language and well-formed bindings (`desktop/src/follow.test.ts`), and listens on nothing; web security and the core CSP stay enabled. Only the exact core origin can navigate a main frame or open native windows; external HTTP(S) links open in the browser and other schemes are denied. Webviews are disabled. Only the main window relaxes the autoplay policy, for notification sounds (`desktop/src/policy.test.ts`). Permissions are denied except notifications, clipboard reads, sanitized clipboard writes and the File System Access API from the core origin inside a core window (`desktop/src/policy.test.ts`). Clipboard reads let VS Code paste from other apps, as the browser UI allows its VS Code frame after the browser's prompt; core-origin content (VS Code, its extensions' webviews) can therefore read the clipboard without a prompt. File System Access lets VS Code's **Download…** save folders and large files: it reaches only files and folders the user picks in the native dialog, and Electron keeps system folders out; a browser asks before it grants the same. |
| Desktop launcher orphaning or attaching to the wrong core | The shell accepts readiness only from its own child pipe and checks its loopback URL and port. Bind failure never reuses another service. Parent-stdin EOF cancels the core; normal quit sends SIGTERM, waits for cleanup, then kills only that child after 20 s. Single-instance locking is per Electron profile. |
| Accidental exposure of the port | Listens on loopback by default; a non-loopback `--listen` is refused unless a proxy secret is configured or `--insecure-listen` is given. |
| Requests bypassing the proxy | `--proxy-secret-file`: requests not from a same-host browser must carry `X-herdr-ide-Proxy-Secret` (constant-time comparison); the header is stripped before reaching code-server. |
| DNS rebinding, cross-site WebSocket hijacking | Host and Origin must be loopback or an `--allowed-origin`. |
| Clickjacking, script injection through served files | CSP with `script-src 'self' 'wasm-unsafe-eval'` and `frame-ancestors 'self'` on every page of the UI, the app shell served for any of its client-side routes included (an `/api/…` path no route takes is 404, not the shell): scripts only from the core's origin, no `eval` or inline scripts; `'wasm-unsafe-eval'` lets the page compile WebAssembly, the terminal emulator served from the same origin (its digest checked by `make check`) and the small module the page builds to hand it callbacks ([26](docs/features/26-web-terminals.md); `TestCSPOnAppShell` pins the policy on the shell, a client-side route and an unknown API path); files are served with `nosniff`, a sandboxing CSP, and HTML/JS as `text/plain`; code-server responses get `X-Frame-Options: SAMEORIGIN`. |
| Local services of a machine running with the UI's origin | code-server's port proxy (`/proxy/<port>/`, `/absproxy/<port>/`) is disabled (`--disable-proxy`) and the core refuses those paths in any case (audited as `denied.port_proxy`), also for a code-server started by an earlier build. Otherwise a page served by any process listening on the machine, including another user's on a shared machine, could script `/ws`. |
| A read-only page making machines reconnect | A read-only page's `retry` over `/ws` is refused and audited as `denied.retry`, and the machine keeps its session (`TestReadOnlyRetryKeepsTheSession`, `internal/server/server_test.go`), since a connection attempt may start an ssh login; a writable page's `retry` only ends the wait before a disconnected machine's next attempt. |
| Paste injection | The page's emulator encodes pastes with Ghostty's paste encoder: bracketed when the program asked for it, with unsafe control characters (ESC among them) replaced, so a paste cannot end itself early or carry escape sequences (`web/src/__tests__/vt.test.ts`); the macOS application's Ghostty does the same. The core passes terminal input on unchanged: a client allowed to write a terminal can type anything into it anyway. |
| Downloads exposing files | `GET /api/m/{id}/download` serves what `/file` already serves, to the same guarded origin: one file as an attachment, anything else as a zip the agent streams (at most 1000 absolute paths; the agent follows the paths named when they are links but stores links below them as links, and leaves out sockets, devices and FIFOs, so a download neither escapes into linked trees nor blocks on a FIFO). Nothing is written on the machine; a cancelled download closes the agent's stream, which stops the walk. Responses carry `nosniff` and the sandboxing CSP, are allowed in `--read-only` like viewing files, and are audited as `file.download` (`internal/server/download_test.go`, `internal/agent/archive_test.go`). VS Code's **Download (folders as zip)** sends paths the bridge extension took from the explorer to the browsers; only a page with the focus downloads them. A download started with a page's random id (`dl=`) is reported as progress events (id, saved name, sizes, state, a reason code; never contents) only to the page that follows that id over its WebSocket (`download.watch`), so other pages, read-only ones included, learn neither the names nor the ids; it can be broken off with `download.cancel`, which needs that id, changes nothing on a machine and is audited as `file.download.cancel`; every download in progress is followed (its state goes with its request), how one ended is kept 10 minutes (at most 256) for a page that reconnects, and one cancelled before its request arrived is refused (`TestDownloadProgress`, `TestDownloadEdges`). An archive is complete only with the agent's end mark: one cut short by a lost connection aborts the response instead of saving a truncated zip. |
| Uploads replacing or escaping files | Uploads go to the machine's upload directory under a name the server makes, or, for files dropped on a pane, into an existing absolute directory the browser names, under the file's base name without control characters; the agent claims that name (or `-1`, `-2`…) with an exclusive create, so an upload replaces no file and follows no symlink there (`internal/server/server_test.go`, `internal/agent/agent_test.go`). Uploads are at most 4 GiB, refused in `--read-only` and audited; a browser allowed to upload can already write anywhere through a pane's shell. |
| Pane programs writing the browser's clipboard (OSC 52) | Terminal output is not trusted, and Chromium and the desktop app (which grants clipboard writes to the core origin) would let the page write the clipboard without a prompt. The page's emulator takes a program's write (up to Ghostty's limit; a read-only page ignores them, `web/src/vt/clipboard.ts`). With the browser setting **Programs copying to the clipboard** at **Automatic** (the default), the browser writes it at once only within 10 s of a key, text, paste or button press it sent to a terminal, the way programs answer a selection or a yank, and a toast shows the length and start of what was copied; any other write, and any write with **Ask**, is shown in a toast whose **Copy** button writes the clipboard; **Off** ignores them. A write that passed the automatic gate is also kept, for its machine only, until the next key, text, paste or left/middle press in a terminal or 2 minutes: meanwhile the pane menu's **Copy** and ⌘/Ctrl+C without a page selection copy it and show the same toast; writes shown with **Ask** are never kept (`web/src/__tests__/clipToast.test.ts`). Reading the clipboard (OSC 52 `?`) is never answered. Residual: during those 10 s any program in a terminal the page shows replaces the clipboard without a click, also after input the user did not type (text VS Code sends to an agent); the toast shows only the first 60 characters. Terminals that allow OSC 52 writes (kitty, WezTerm, Ghostty) allow them at any time. **Ask** keeps every write behind the button. |
| Links in pane output (OSC 8) | Only `http:`, `https:` and `mailto:` targets are underlined or opened, with ⌘/Ctrl+click; the tooltip shows the real target. |
| Other users on the core host hijacking ssh | ssh control sockets live in `/tmp/herdr-ide-<uid>/s`, which must be a directory owned by the user with no group/other access, or the core refuses to start. |
| Other users on a machine | Agent state is in `~/.herdr-ide` (0700); code-server and the bridge listen only on unix sockets there (0600); nothing listens on TCP. |
| Tampered downloads | code-server releases and extensions are verified against pinned SHA-256 digests or `.sha256` sidecars; mismatches are refused. |
| Archive path traversal | Tarball extraction rejects absolute paths, `..` and links leaving the install directory. |
| Downloads made by machines (`--code-server-install=download`) | The machine fetches only `http(s)` URLs built from the core's `--code-server-url` template, with curl or wget and no shell; the tarball is checked against the digest the core knows before it is unpacked. A digest learnt on first use is recorded on the core like the core's own downloads. |
| The macOS application (`macos/`) | It talks only to a core on loopback: the one it starts from its bundle with `--parent-stdio` on a port of the system's choice, taking the URL from the core's ready line only when its host is loopback, or the one named by the development variable `HERDR_IDE_CORE`, which is honoured only with the same check (`http(s)` to `127.0.0.1` or `localhost`, `CoreProcess.loopbackURL`, `CoreProcessTests`), over `/api/v1/term` and the event channel `/ws`. Terminal output goes to Ghostty's emulator; a link opens only on a ⌘-click, web and mail links in their applications, anything else as a path: opened in VS Code through the core's bridge, or fetched from the machine into a private temporary directory (0700, emptied when the next preview is complete and at quit) and handed to the system's Quick Look, never opened or run on this Mac; the file is streamed into a file of its own (0600) and refused before a byte is written when its length is over 512 MiB, or stopped and removed once 512 MiB arrived without one (`BoundedDownload`, `BoundedDownloadTests`). A program's clipboard write (OSC 52) reaches the clipboard by itself only within 10 s of the user's own input to a terminal under `terminal.programClipboard` `auto`; otherwise a note offers to copy it, and `off` refuses it (`Activity.clipboardWrite`, `macos/Tests/TermKitTests`). Pasted and dropped files are uploaded only by the user's paste or drop, through the core's upload endpoint, and only their paths are typed. Its web views (VS Code, program windows, the formula preview's `/math.html`) load only the core's origin, addressed as `localhost`; `about:`, `blob:` and `data:` documents load only in frames inside its pages, and as the page itself only the empty `about:blank` (`WebNavigation`, `WebNavigationTests`); navigation elsewhere is cancelled and web links are passed to the browser, and `window.open` creates no window in the application. The terminal renderer is fetched at build time by `scripts/fetch-ghostty.sh`: a pinned tag of the Swift package accepted only when it is the pinned commit (its full 40-digit id, checked again before a checkout fetched earlier is reused), and the binary framework checked against a pinned SHA-256; SwiftPM downloads nothing itself. `scripts/macos-app.sh` signs the core inside the bundle and then the bundle with the hardened runtime, and fails unless `codesign --verify --deep --strict` accepts it; the signature is ad hoc unless `SIGN_IDENTITY` names a certificate, and notarized only with `NOTARY_PROFILE`. |
| Terminal clients (`/api/v1/term`) | The WebSocket passes the same Host, Origin and proxy-secret guards as every request. herdr-core's API also runs commands, reads and writes files and reaches other machines; clients get only an allowlist of methods about terminals and documents (`termReadMethods`, `termWriteMethods` in `internal/server/term.go`), never `machine.*`, `file.*`, `server.*` or a call with `on` (another machine of that core); refused calls are audited (`denied.term`, a call refused for `on` included), and `terminal.run` (its `argv`, `cwd` and the names, never the values, of the variables the client gave in `env`), `terminal.kill`, `terminal.rm`, `terminal.interrupt` and `terminal.keep` are audited with their terminal; an `env` that is not an object of strings is refused. Attaching is a message of its own, so a client cannot open herdr-core channels itself. Output is credited end to end: a client's `ack` returns at most the output the core sent it on that stream and it has not acknowledged, so it cannot make a terminal core send ahead of what it draws, and a client that stops reading is disconnected (`TestTermProtocol`, `internal/server/term_test.go`). |
| Read-only terminal clients | With `--read-only` a client of `/api/v1/term` may subscribe to machines, call the reading methods (`terminal.list`, `terminal.get`, `terminal.read`, `doc.get`, `templates.list`) and attach as an observer; writing methods are refused (`read_only`). An observer's attach carries no display facts and cannot take the terminal's size; its input, automatic input, `resize`, `focus` and `facts` are dropped; its focus does not mark an agent's finished turn as seen for other clients; its credit is cut to the output it was sent. The core installs, starts and restarts no terminal core for it (`TestTermReadOnly`). |
| Large messages on the terminal protocol | `/api/v1/term` reads messages of at most 16 MiB; a larger one ends the connection. |
| Connections to machines' terminal cores | A machine's terminal backend (the core's connection to that machine's terminal core through the agent) is opened by its first subscriber and closed 10 s after the last subscriber left; the terminal core and its programs keep running there, as they belong to the user's account, until stopped from the UI. |
| The agent's herdr-core (ops `hc`, `hc-api`) | herdr-core's API has no authentication of its own: whoever reaches its socket runs commands as the user. The agent puts the socket in its run directory (0700), sets the socket itself to 0600 after a start and a restart (herdr-core creates it 0755 and relies on the directory), and reaches it only through the `hc-api` pipe; nothing listens on TCP. The executable is written to a temporary file in `~/.herdr-ide/hc/` (0700), accepted only when its SHA-256 equals the digest sent with the install (64 MiB at most), and then renamed into place (`internal/agent/hc_test.go`). Before a start or a restart the core sends the digest of the executable this build carries, and the agent hashes the installed file again (not from its cache) and runs it only when they are equal (`bad_digest` otherwise); a development build that carries no executable sends none, and the installed one runs (`TestHCVerifiedBeforeStartAndSocketPrivate`, which checks the socket's mode after both as well). The session name and the socket are the agent's own (its instance), never taken from a request, and commands run with `HC_SESSION`, `HC_SOCKET` and the terminal variables of the agent's environment replaced, so they cannot act on another herdr-core of the user. Programs in its terminals inherit `HC_SESSION` and `HC_SOCKET`: herdr-core commands typed there reach this core. The variables of a terminal or multiplexer the agent itself runs in (herdr-core's every `HC_*`, herdr's `HERDR_*`, among them its socket path, tmux's `TMUX`, screen's `STY`, zellij's) are not passed to anything it starts, so programs in its terminals do not reach the herdr session or tmux server a core was started from (`TestCleanEnv`, `internal/agent/procutil_test.go`). |
| Other users on a machine reaching the virtual display | Xvfb accepts only clients presenting its MIT-MAGIC-COOKIE-1 and runs with `-nolisten tcp`. The cookie is new at every Xvfb start and names the display; Xvfb reads its own copy (`run/xauth.server`), terminals get `run/xauth` (both 0600 in the 0700 run directory), so a program changing its `XAUTHORITY` file cannot leave the server without a cookie. |
| Another user posing as the X server | X sockets live in world-writable `/tmp/.X11-unix` (libxcb before 1.16 cannot use another path), abstract ones in a namespace without permissions, and X clients cannot authenticate the server. The agent therefore uses a display number only while no lock file, socket or listener of another user is on it and `/tmp/.X11-unix` is a directory of root or the user that is sticky or not writable by group and others; it sends the cookie only to a server whose peer credentials (`SO_PEERCRED`) are this instance's Xvfb on the connection and on both its sockets (filesystem and abstract), and terminals get `DISPLAY` only from a display verified this way. Residual: a terminal created earlier keeps `DISPLAY=:n` after its display ended, and a program started there later reaches whatever server then takes `:n`. A display ends a minute after its last client; while the instance's terminal core runs the display keeper is a client (the core asks for one whenever the display is ready and each time the terminal core becomes reachable), so this needs the keeper gone with the terminal core still running (killed, or the terminal core restarted while the core was away); another local user who binds the abstract names of every candidate number (`:20`–`:519`) can make program windows unavailable. |
| Input to programs' windows from the browser | Window pages and their WebSockets pass the same guards as panes (Host/Origin, proxy secret, app CSP); frames are images; commands to the agent are built by the core (a viewer's refresh carries the streams all viewers decode, not its own list), and a viewer holding 64 frames or 16 MB it has not shown skips frames; closing a window (`POST /m/{id}/gui/{win}/close`, sent with `keepalive`) needs the page's own Origin like every mutation. Pages use `Referrer-Policy: same-origin`, so same-origin requests carry their Origin and other sites get no referrer. In `--read-only` mode viewers send no input, closing is refused, and a viewer can neither acknowledge frames it was not sent nor ask for the whole window more than twice a second. |
| Programs on one display | X11 does not isolate clients: every program on a machine's display (from any terminal of the instance) can read and control the other windows on it, as on a desktop. |
| Fetching Xvfb on machines | Happens when a remote Linux machine connects with the GUI setting on for it, never in `--read-only` mode (which only shows a display that already runs); audited as `gui.install` and `gui.start`. `apt-get download xvfb` verifies the package against apt's signed lists (not for sources marked `[trusted=yes]`); it is unpacked with `dpkg-deb -x` into the user's `~/.herdr-ide/xvfb/` under a validated version name. Nothing runs as root. |
| Running the video encoder on machines (`gui.video`) | On by default for remote Linux machines, per machine in the settings, never pushed in `--read-only` mode. The core pushes the encoder it embeds (built from pinned, checksummed sources by `scripts/build-ffmpeg.sh`; releases build it in CI) through the agent; the agent writes it to a fresh temporary directory, compares its SHA-256 with the digest the core sent, moves it into `~/.herdr-ide/video/<digest prefix>/` (0700) and runs it only while the file there still has that digest when first used by the agent. Pushing is audited as `gui.video`. The encoder runs as the user with the agent's environment, reads raw frames from a pipe and writes packets to one; it opens no network connections, and no files beyond the GPU's: NVIDIA's driver libraries, or a render node the user may open (`/dev/dri/renderD*`) and the VA-API driver for it, which the libva built in loads from the distribution's driver directories (`/usr/lib/<triplet>/dri`, `/usr/lib64/dri`, `/usr/lib/dri`; not `/usr/local`, which a group may write) or from `LIBVA_DRIVERS_PATH`, the user's own setting. Windows larger than 4096 pixels a side are never captured whole for video. Browsers name the streams they decode in `?video=` (at most four short lowercase names); frames stay inside the guarded WebSocket like pictures. |
| Capturing windows through shared memory | The agent's window manager reads window contents through MIT-SHM into a System V segment created 0600 (only this user can attach it) and, on Linux, marked for removal as soon as the agent attached it (Xvfb attaches it afterwards), so it disappears with the agent and the display even if the agent is killed meanwhile. Other clients of the display could name the segment, which gives them nothing beyond what any program on one display can already do (see below). Without MIT-SHM, or when the segment fails, captures go through the X connection. |
| The display keeper | `herdr-ide-agent gui-keep`, started by the agent when the core asks (audited as `gui.keep`; never in `--read-only` mode), runs as the user and opens the instance's display like the agent: with the cookie, only to the Xvfb the instance recorded (peer credentials). It follows the server that listens on the instance's terminal core socket and is the user's (`SO_PEERCRED`), telling it from a later process by its start time; it sends it nothing (it connects and closes) and exits when it is gone. |
| VirtualGL in every program of a terminal (`--gui-gpu=all`) | Opt-in; preloads only VirtualGL's faker libraries found in system or `/opt/VirtualGL` library directories, by their resolved path, and only when the library and every directory above it belong to root and cannot be written by group or others. |
| Typing into terminals to enable program windows | `POST /api/m/{id}/gui/enable` is a mutation (same guards, refused in `--read-only`, audited as `gui.enable` with the terminals typed into). A terminal's shell is found from its record read at that moment (`terminal.get`: its program and the foreground process group's leader), and the text is input of a short attach at the terminal's own size, so no viewer's size changes (`internal/server/term_test.go`). The core types only into known shells (bash, zsh, fish, dash, sh, ksh and similar, by executable name, so not into a program that replaced its shell with `exec`) waiting at their prompt (their process group is in the foreground, checked again right before typing): first Ctrl-C, which discards a half-typed command line, then only ` export` of the display variables it computed, each value single-quoted. A shell running a builtin such as `read` also looks idle; the text then goes to it. The audit record lists the terminals typed into, busy and unreachable, also when the request fails. |
| Per-machine settings | `PUT` and `DELETE /api/settings` with `machine` pass the same guards, accept only machines the core knows, settings whose scope allows machine values and, for remote-only settings, remote machines; a command-line flag still fixes the value for every machine. |
| The display in new terminals | A `terminal.run` through `/api/v1/term` on a remote machine with its display ready gets `DISPLAY`, `XAUTHORITY` (and VirtualGL's variables when set) in its `env`, replacing values the client sent for them, so a client cannot point new programs at another X server through these names; other variables pass unchanged, a malformed `env` is refused, and the audit entry of `terminal.run` names the variables added (`internal/server/term_test.go`). The values are those the agent verified for the instance's own display. |
| Agent detection in the agent | Op `detect` reads the screens of the user's own terminals in the instance's terminal core (`terminal.read`) and their foreground processes, as the user, next to the terminals; it sends the core only an agent's name and one state word per change, never screen text, keeps nothing on disk, and starts nothing. Its observing attaches never type or resize. The rules are data embedded in the agent (herdr's manifests, checked against limits of size and nesting); its regular expressions are Go's RE2, which runs in linear time, so a screen cannot make a rule take long (`internal/agent/detect`). |
| Changing settings from the UI | `PUT` and `DELETE /api/settings` pass the same guards as every other request (Host/Origin, proxy secret), are refused in `--read-only` (403), accept only defined settings with typed, validated values (booleans, numbers in range, enum values, `#rrggbb` colors, lists of a fixed length, absolute paths; strings without control characters (C0, DEL and C1) and at most 4 KiB, bodies at most 64 KiB), and are audited (`settings.set`, `settings.reset`). A setting given on the command line cannot be changed. The code-server path chosen there is run on the machines, which gives no more than the shell access the UI already has. Terminal settings become lines of the macOS application's Ghostty configuration; strings without line breaks cannot add others (`internal/settings/settings_test.go`, `internal/server/settings_test.go`). |
| Changing keybindings from the UI | `PUT /api/keybindings` passes the same guards, is refused in `--read-only`, accepts at most 1000 rules (256 KiB) whose keys parse, whose commands are short identifiers and whose `when` is one of four words, and is audited (`keybindings.set`). A binding only chooses which of the UI's own commands a key runs. |
| The settings and keybindings files | `settings[-<instance>].json` and `keybindings[-<instance>].json` on the core host are written atomically with mode 0600 in the product's configuration directory, which is created 0700; an existing one that is a directory of the user's and open to others is made 0700 at the next write, and a link to a directory is left as it is (`internal/userfile/userfile_test.go`). Edits by hand are read again (polled every 2 s) and validated like API changes: invalid entries are ignored and reported, never executed; a file that is not JSON is never written over. Changes, whatever their source, are pushed to every `/ws` client; they carry values and bindings only, which those clients may read through the API anyway. |
| Adding, removing, renaming, enabling and disabling machines from the UI | `POST /api/machines`, `PUT /api/m/{id}/label`, `PUT /api/m/{id}/enabled` and `DELETE /api/m/{id}` pass the same guards as every other request, are refused in `--read-only` and are audited, with the error when one failed (`machine.add` with id, target and label, `machine.rename` with the old and new label, `machine.remove` with the target, `machine.enable`, `machine.disable`; `internal/server/machines_test.go`). A target holds only letters, digits and `. _ - @ : / [ ] %` (`[user@]host[:port]`, `[IPv6]`, `ssh://` URLs, `~/.ssh/config` aliases), at most 255 bytes, and does not start with `-` (`machines.ValidTarget`); stored records and machines imported from herdr's catalog that fail it are dropped, an `--ssh` target that fails it stops the core at start, and every ssh command puts `--` before the target, so a target never reads as an option of ssh nor carries a shell metacharacter (`TestValidTarget`, `TestRegistryDropsInvalidTargets`, `TestSSHTargetAfterDoubleDash`); a label has no control characters and at most 64 characters; bodies are bounded (4 KiB). The core runs nothing to add a machine: it stores the record and connects with the user's ssh configuration and BatchMode, as for every machine; an interactive login happens only in the authentication terminal the user opens. The id of a new machine is random, never derived from the target. The records are kept in the core's own `machines[-<instance>].json` (beside the settings, 0600, replaced atomically); a file that cannot be read is never written over. herdr's catalog is read once, to import it, and never written. Removing or disabling ends the machine's agent session, which stops what the agent started there (code-server); programs keep running there. The local machine cannot be removed or renamed. |
| Starting, stopping and restarting a machine's terminal core from the UI | `POST /api/m/{id}/hc/{start\|stop\|restart}` passes the same guards, is refused in `--read-only`, accepts only these three actions for machines the core knows, and is audited (`hc.start`, `hc.stop`, `hc.restart`, with the error code; `internal/server/term_test.go`). It runs the agent's `hc` op for the instance's own session and socket, which starts or restarts the installed executable only after hashing it again and finding the digest of the executable this build carries (see the agent's herdr-core above); a start installs this build's executable first like a subscription does. Stopping ends the programs of the user's terminals there, which the UI asks before; the core then starts no terminal core for that machine until it is started again or a client subscribes anew. `GET /api/m/{id}/hc` reports the status only (digest, version, session and socket path), also read-only. |
| Release signing secrets | The release workflow's optional Developer ID certificate, its password and the notary's credentials (`MACOS_*` secrets) are given to one step, which signs the macOS application again and notarizes it (`scripts/macos-app.sh sign`) in a keychain it deletes when it ends; the build, its tests and the other jobs run without them. Only the publishing job may write to the repository. Every action of the workflows is pinned by its full commit id (`.github/workflows/`). |
| Accountability | `--audit-log` records connections, mutating calls (with the working directory of new terminals and the names, never the values, of the environment variables the client gave them and the core added), uploads, VS Code and bridge use, provisioning and closing program windows, and refusals. |

Not provided by herdr-ide: user authentication, TLS, rate limiting, per-user
authorization. Use the reverse proxy for these.

The desktop core has the same loopback HTTP trust boundary as CLI local use;
the launchers (the Electron shell and the macOS application) do not add
authentication against other processes on the host. The Electron app/DMG
build uses ad-hoc signing, not Developer ID signing or Apple notarization.
Do not treat the build as a notarized public release. The DMGs attached to
GitHub releases are built the same way by the release workflow. The macOS
application attached to a release (a zip) is signed ad hoc too, unless the
repository holds the optional Developer ID certificate and notarization
credentials as secrets ([RELEASING.md](RELEASING.md)), which only the
step that signs and notarizes it receives (see the table). The integrity of release files
rests on `SHA256SUMS` and, for a public repository, GitHub build-provenance
attestations, both covering archives, DMGs and the zip. Only the final
publish job of that workflow holds write permissions; the build jobs read
the repository.

## Embedded herdr-core

The core embeds upstream herdr-core for the agent to install on machines
([21](docs/features/21-terminal-core.md)). The build downloads the release
archives and checks them against SHA-256 digests pinned in
`internal/hcdist`; it fails on a mismatch. The executable is taken from the
same bytes that were verified, as the one regular file named `herdr-core`
at the archive's root (64 MiB at most; a link, a directory or a second entry
of that name is refused), and is never run during a build
(`internal/hcdist/release_test.go`). The core hands the agent the SHA-256
of the uncompressed executable with every install
(`internal/embedded/embedded_test.go`), and the agent accepts only a file
with that digest.

## Supported versions

Security fixes go to the latest release and to `main`.

## Reporting a vulnerability

Please report privately instead of opening a public issue: use the
repository host's private vulnerability reporting ("Report a vulnerability"
under the Security tab) or contact the maintainers. Include the version
(`herdr-ide version`), configuration flags and steps to reproduce. You will
get an acknowledgement within a few days.
