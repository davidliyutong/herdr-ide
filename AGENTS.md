# AGENTS.md

Instructions for coding agents (and humans) changing this repository. Read [docs/architecture.md](docs/architecture.md) and the relevant [feature design document](docs/features/README.md) before non-trivial changes.

## What this is

The hub (`backend/`, TypeScript, built with Bun into one executable per platform; [its README](backend/README.md)) serves a React terminal UI and reaches several machines over ssh through a per-machine agent: the machine side in TypeScript ([42](docs/features/42-typescript-backend.md): `backend/machine`, `backend/hosts/machine` and the features' `machine.ts`), its command `node` serving the hub's protocol. Each platform's executable is the hub and that platform's machine side (the machine build); a machine downloads its platform's release archive from GitHub (`<slug>-<platform>.tar.gz`, checked against the release's `SHA256SUMS`), or the hub uploads it. Every machine's terminals live in a terminal core of the agent's own (herdr-core, `hc`, in a session apart from the user's); the browser emulates them with Ghostty's libghostty-vt as WebAssembly through the hub's terminal protocol (`/api/v1/term`), and an Electron desktop app (`desktop/`) wraps the same UI and a hub of its own on macOS, Windows and Linux. The agent runs on Linux and macOS only, so a hub on Windows reaches SSH machines only. code-server provides VS Code panels. A chat host on each machine (the command `chat-host`, a hidden terminal of that terminal core) runs coding agents headless for the chat panes, its state in SQLite (`backend/shared/store`). The hub's executable embeds the UI, its platform's herdr-core (with the digests of every platform's) and, on Linux, video encoder, and a VS Code extension. A node of this build takes over from a node of an earlier release still running on a machine ([42](docs/features/42-typescript-backend.md)).

## Tests: standard and extended, by group

Every test belongs to one group, selected by location and name:

- A feature: `cd backend && bun test features/git`; its web UI: `pnpm -C web test git`; its e2e spec: `make e2e E2E_ARGS='tests/git.spec.ts'`.
- A kernel part: `bun test kernel/config` (in `backend/`); the machine side: `bun test machine`; the hosts: `bun test hosts`; a shared library: `bun test shared/store`; the build's scripts: `bun test scripts`.
- A web UI area, one file per area in `web/src/__tests__`: `pnpm -C web test term`.
- The desktop shell, beside its sources in `desktop/src`: `pnpm -C desktop test hub` (no argument: the whole shell).
- Cross-cutting contracts are a group of their own: the wire protocols (`bun test shared/proto`), the agents' kinds and transcripts with the vectors of `spec/vectors` (`bun test shared/agents`, `pnpm -C web test transcriptVectors`, the terminal keys' `vt-keys.json` run by the vt tests).
- Integration (`make it`), end-to-end (`make e2e`) and the machine matrix are groups of their own, each with its own target above.

Each group is split into **standard** and **extended** tests:

- **Standard** tests run in `make test` and on every change to their group: fast, deterministic, independent of the machine they run on (a temporary `HOME`, no network, no tools beyond the documented toolchain, free ports only). Run `make check` and the groups a change touches; run `make test` before merging and after a change that crosses groups (a protocol, a shared module). Do not run the whole suite after each edit.
- **Extended** tests wait on real time, programs, compiles, Docker or large inputs, or give little benefit for their cost. One marker in every suite: `extended`/`extendedDescribe` of `backend/shared/testdata/extended.ts` (hub), `web/src/__tests__/extended.ts` (web UI) and `desktop/src/extended.ts` (shell), all skipped unless `EXTENDED_TESTS=1`. Run one file with `EXTENDED_TESTS=1 bun test <file>` (likewise `pnpm -C web test <file>`, `pnpm -C desktop test <name>`), everything with `make test-extended`. CI runs standard and extended. `make it`, `make e2e` and the machine matrix cost minutes and load the machine: run them only for what they cover, the whole set before a release.
- Never add load (stress tools, busy loops) to the user's machine to provoke a failure.

## Local test environment (`.env`)

Machine-specific test targets and paths (such as a physical Linux KVM/GPU host `LINUX_TEST_HOST`, optional `LINUX_TEST_SSH_OPTS`, remote Windows host `WIN_TEST_HOST`, golden Windows disk `WINVM_BASE`, `E2E_CODE_SERVER_SEED`, `MACHINES_*`, `ACT_*`) live in a **gitignored `.env`** file at the repository root, documented in [`.env.example`](.env.example).

- **Recognized automatically** by `make test-remote`, `make test-win`, `make it`, `make e2e`, `make test-linux`, `make ci-local`, `make test-doctor`, `e2e/machines/machines.py`, and `e2e/machines/winvm.py` via a non-executing key=value parser (`scripts/load-env.sh`; explicit env/CLI flags always win; `DOTENV_DISABLE=1` disables it). Standard unit tests (`make test`) never read `.env`.
- **For coding agents**: before concluding that a Linux KVM host, GPU host, Windows VM, or `code-server` seed is unavailable, check `.env` (or run `make test-doctor`, which reports whether `.env` is configured and gitignored). Use `make test-remote` or `e2e/machines/machines.py remote -` when `LINUX_TEST_HOST` is set, and `make test-win` when `WIN_TEST_HOST` or `WINVM_BASE` is set.
- **Security**: `.env` is ignored by `.gitignore`, excluded from `winvm.py` / `test-remote.sh` snapshot uploads, and not passed into `act` containers (`--env-file /dev/null` by default). Never commit `.env`, never print secret values from it, and keep SSH private keys outside the repository (`~/.ssh/` or a `chmod 600` config referenced via `*_SSH_OPTS`).

## Rules

1. **Never touch the user's real instance or terminals.** Experiments, tests and dev servers use `--instance dev` (state in `~/.veldr-dev`, terminal core session `veldr-dev-<host id>`), the integration tests' sessions `veldr-it` and `veldr-it-<host id>` or the end-to-end tests' instances `e2e-<random>` (homes in `/tmp/hie-*`, SSH machines in Docker containers labelled `veldr.e2e`); the desktop app's instance (`desktop`) and the default one are the user's. Stop a terminal core only through its own instance (`POST /api/m/{id}/hc/stop` of the dev hub), never the user's, and do not attach to the user's terminals.
2. **No hardcoded product name.** Use `backend/shared/lib/brand.ts` (the hub), `APP_NAME`/`APP_SLUG`/ `storage` from `web/src/brand.ts`, `src/brand.ts` in the extension. `scripts/check.sh` fails otherwise. Renames: `scripts/rename.sh`.
3. **All UI text through i18n.** Add the key to `web/src/i18n/en.ts` and the translation to `zh-CN.ts` (the build fails if one is missing); a plugin's messages are in its own `web/src/plugins/<id>/i18n/` instead. The server returns codes, not prose. Comments, logs and identifiers are English.
4. **Docs move with code.** New or changed flags and endpoints → `docs/reference.md` (CI checks with `backend/scripts/reference.ts`; its settings and commands tables are generated by `make tokens`); protocol or component changes → `docs/architecture.md`; behavior and its reasoning → the feature's `docs/features/NN-*.md` (new features get a new document following `docs/features/README.md`); operations → `docs/deployment.md`; user-facing summary → `README.md` and `README.zh-CN.md` (same sections). Documents on `main` describe the system as it is: no TODO, TBD or open questions in files or code comments. A design for work done in stages may describe its goal on its branch; the branch merges into `main` once the code matches the document. Report open items to the user so they are tracked in the issue tracker.
5. **Keep the security guardrails.** Loopback by default, Host/Origin checks, proxy secret, the terminal protocol's method allowlist, read-only mode, 0700/0600 unix sockets, nothing listening on TCP on machines, verified downloads. Changes here need a test and a note in `SECURITY.md`.
6. **Bound remote resources.** Anything started on a machine must have an owner and a way to end (agent exit, idle timeout, explicit stop); anything written to disk needs a retention rule. Document it in `docs/deployment.md#remote-resources`.
7. **Protocol compatibility.** Hub and agent ship together, but extend the agent protocol (`backend/shared/proto/agentproto`) by adding fields/ops: nodes of earlier releases speak it until a node of this build takes over. herdr-core's API is external: speak its protocol generation (`backend/shared/proto/hc`), honor stream credit, and take a `missed` notification as the subscription's new complete state.
8. **Tests.** The hub's beside its sources in `backend/` (`<name>.test.ts`, `bun test`; machine-side tests use a temporary `HOME`); web tests in `web/src/__tests__`; the desktop shell's beside its sources in `desktop/src`. A test may not depend on the developer's machine: a temporary home, no network, no fixed ports, no tools beyond the documented toolchain (an absent optional tool skips with a reason, and the test is extended). Don't add tests that need network access or real machines to `make test`. A test that waits on real time for what runs in the background (a timer, a program, a worker) waits generously and is marked `extended` (`backend/shared/testdata/extended.ts`, `web/src/__tests__/extended.ts`, `desktop/src/extended.ts`): `make test` skips it, `make test-extended` and CI run it.
9. **`CHANGELOG.md` changes only in a release.** Feature and fix branches do not touch it. When a release is cut, a `release-manager` subagent writes the version's entries from the pull requests merged since the last tag ([RELEASING.md](RELEASING.md)).

## Agent roles

Reusable specialist roles live in [`.claude/agents/`](.claude/agents/) (Claude Code subagents; other agents can follow the same files as playbooks):

| Role | Use it when |
| --- | --- |
| `hc-integration` | Changing anything that talks to the terminal core (herdr-core), or upgrading it. |
| `security-reviewer` | Only when a code review is asked for, or before merging a branch that changes guards, files, sockets, processes, ssh or downloads; not after every change. |
| `docs-keeper` | After changing flags, shortcuts, protocols, layout on disk or features; or to slim the docs (unwrap, drop outdated content, refresh screenshots, collect disclaimers and history into `docs-review/` for review). |
| `i18n-translator` | After adding or changing user-visible text, or to add a locale. |
| `release-manager` | Cutting a release (it writes `CHANGELOG.md`) or bumping pinned code-server/extension versions. |
| `oss-steward` | Auditing open-source health before releases or after restructurings. |
| `code-slimmer` | Removing backward-compatibility code, unused code and defensive structure; it reports a plan first and changes code only once the plan is approved. |
| `test-curator` | Grouping tests by subsystem, making them independent of the machine, sorting them into standard and extended, deleting badly designed ones. |
| `perf-reviewer` | A performance and robustness review: polling, caches, unbounded resources, retries and backoff, algorithms, concurrency, races between hub and nodes. Read-only. |

## Gotchas

- Key events in the browser's terminals are encoded by Ghostty's encoder (`web/src/vt/input.ts`, `vt/pane.ts`), and a keydown that sent bytes is cancelled; an uncancelled keydown is followed by a keypress and an input event that would send the text again. Any key the UI translates or leaves to the browser needs a row in `web/src/__tests__/testdata/vt-keys.json` with its bytes in each mode.
- Native submodules (`veldr-vt`, `veldr-encoder`, `veldr-gpupick`, `veldr-gui-helper`) live in their own `davidliyutong/veldr-<slug>` repositories with independent CI/CD releases, pinned by version and SHA-256 in `backend/scripts/deps.ts` and fetched by `backend/scripts/fetch-deps.ts` (`make deps` / `scripts/build.sh`); `libghostty-vt`'s functions read and write wasm memory, whose buffer may change after any call, so take views again after each one.
- `gui-helper`'s wire messages with the node are `src/proto.zig` (in `davidliyutong/veldr-gui-helper`) and `backend/features/gui/machine/helper.ts`, changed together when extending the protocol.
- yamux streams cannot be half-closed: use `ChunkWriter` (agentproto) for uploads that expect a reply.
- A coding agent kind is a row of `backend/shared/agents/kinds.ts` with a detector manifest of the same id (`backend/features/agents/machine/detect/manifests`, which `MANIFEST_FILES` of `manifests.ts` beside it lists; `kinds.test.ts` compares the registry with them and the settings, and `UPDATE_TESTDATA=1 bun test features/agents/machine/detect` in `backend/` rewrites what the detector's tests expect them to parse to), then `make tokens`. Finding its sessions needs `backend/machine/agents`. Claude Code's transcripts are mapped to events by `backend/shared/agents/transcript` (the chat host's imports and its Claude Code adapter), specified by the vectors in `spec/vectors/transcript/`, which the hub's and the web tests run; `UPDATE_TESTDATA=1 bun test shared/agents/transcript` in `backend/` rewrites a vector's expected events after a deliberate change of the mapping (review the diff). A chat with it (the chat host running it headless) also needs a `chat` spec in its row, whose `adapter` is one of `ADAPTERS`, the protocols of the adapters behind `backend/features/chat/machine` (`kinds.test.ts`, "chat kinds"); its argv, environment and session metadata stay on the machine's side, never in the registry's JSON. The adapters' protocol recordings are in `spec/vectors/chat/` (sanitized; its README says what each shows and which version made it), what the adapters make of them in each adapter's `testdata/golden`.
- Chat adapters follow the rules in `backend/features/chat/machine/adapter.ts`'s header comment: never write the agents' configuration (a Codex thread starts and resumes read-only and gets its policy per turn; a writable one adds the directory to `~/.codex/config.toml`), end an agent gracefully before any SIGKILL (Codex killed outright leaves its shell snapshots), answer requests they do not serve with "method not found". The app-server schema of Codex the adapter speaks is pinned in `spec/codex-app-server` (the schema Codex prints, the types `backend/scripts/codex-schema.ts` makes of it, checked by `make check`, and `appserver.test.ts`, which holds the recordings and what the adapter sends to it; its README says how to move to another version).
- The TypeScript build's Claude Code adapter runs on Anthropic's Agent SDK, which no executable may carry (all rights reserved): outside tests import only its types (`scripts/check.sh`; `backend/scripts/build.ts` refuses an executable that holds it). Machines fetch the npm tarball pinned in `backend/features/chat/claudesdk.ts`; moving to another version changes the pin (version, integrity, the entry's SHA-256) and the development dependency together (`sdk.test.ts`, `installed.test.ts`).
- A terminal the product runs for itself (the chat host) is hidden by its reserved name and label together (`agentproto.Hidden`, `hidden` of `backend/shared/proto/agentproto`): anything that walks a terminal core's terminals (the hub's terminal protocol, agent detection, terminal history) skips it with that function, never by the label alone, which any program can set.
- Never call herdr-core's `terminal.read` with `lines` above 0 for a read-only client or from a background task: with history lines the terminal core scrolls a program on the alternate screen, which every viewer sees.
- `web/dist` is embedded into the hub's executable when it is built (`backend/scripts/build.ts --web`); `make build` builds the UI first, and `make dev-hub` serves `web/dist` as it is (`--web-dir`).
- Adding an npm dependency of `backend/` changes `THIRD_PARTY_NOTICES.md`; run `scripts/notices.sh`.
- Files many changes touch are laid out so that parallel branches merge: `README.zh-CN.md` has one sentence per line, and enumerations in the docs that grow with features are lists with one item per line.
- macOS limits unix socket paths to 104 bytes; keep socket paths short.
- The hub builds for Windows, the agent does not: the hub's code runs in Bun and in Electron's Node (`shared/`, `kernel/` and the features' `hub.ts` use Node's modules only, `tsconfig.node.json`; the machine side is Bun on Linux and macOS, backend/README.md's rules); POSIX-only tests skip on Windows. Paths on machines are POSIX: use `node:path`'s `posix` for them. `.gitattributes` keeps LF line endings on Windows checkouts.
- The binary a machine gets is its platform's executable from the release's archive, checked against the release's `SHA256SUMS`: the machine downloads it, else the hub uploads it from `--agent-dir`, its cache, its own executable or the release (`backend/kernel/machines/transport/release.ts`, `ssh.ts`), checked by its SHA-256 on the machine. Its command line is `backend/hosts/bun/main.ts` (`node` from `backend/hosts/machine/cli.ts`; the node's features in `backend/hosts/machine/features.ts`).
- Bun's unix socket server removes the path it bound when it closes: the machine side binds every socket under a temporary name and renames it into place (`backend/machine/sockets.ts` `listenUnix`); use it, or a closing server removes a socket another node put there.
- The machine side calls no variadic C function through `bun:ffi` (on macOS/arm64 their arguments go on the stack): `fs.openSync` passes `open`'s flags (`O_NOFOLLOW_ANY` without `O_NOFOLLOW`, which macOS refuses beside it), and Linux's system calls without a fixed-argument wrapper go through `syscall(2)` with integer arguments only (`backend/machine/sys`).
- code-server's webviews need a secure context; test VS Code features on `http://localhost` or HTTPS, not a LAN IP.
